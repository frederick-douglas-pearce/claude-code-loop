## (A) Every point where the engine delegates to a subagent, or could

### Takeaway

The engine names nine distinct spawn roles across steps 1–10 and says **nothing** about which model
or effort any of them runs at: a grep of the whole payload for `model`, `effort`, `haiku`, `sonnet`,
`opus` returns only `disable-model-invocation` and "best-effort". The implement step (6) is the
parent thread by design, every subagent is either read-only or runs in its own isolated copy, and the
only spend control is the per-run `subagent-cap` ledger field, which is "never a binding".

### Inferences

- **Three of the four "cheaper model" roles R4 names do not exist as spawns today.** Ledger probes, step 0/1 reconciliation and CI wait are parent turns; docs propagation and green-up are notebook proposals (levers F and H). The only shipped spawn R4 classifies as cheap-eligible is the mutation selector, plus a contested half of the AC-verifier. So a first tiering PR's measurable surface is narrower than R4's list reads.
- **"Mechanically verified" is a property of a role's *output*, and the AC-verifier's Part 1 fails that test as written.** Its inputs are mechanical (`git diff "$BASE"`, `ls-files`), but what it returns is "met/not-met with the file:line or test that satisfies it" per criterion plus "the complete verdict on EVERY criterion", a judgment the orchestrator may not replace ([accepting.md:113-129](plugins/dev-loop/skills/dev-loop/phases/accepting.md)). R4's "mechanical Part 1 checks" reads as the input-retrieval half; there is no separate spawn for that half today.
- **Re-modeling the implementer has no engine-side lever.** Step 6 runs in the parent, whose `(model, effort)` the harness sets (F167 shows the CLI changing it without asking; the mitigation was a user `modelSettings[...].effortLevel`). The engine can only reach a different implementer model by moving implementation into a writing subagent in an isolated copy, which D017 and R2 both leave in the parent for now. R1's fix agent is the first increment of exactly that move, scoped to fix application. Any design that "tiers the implementer" is therefore either (a) a consumer harness setting outside all three layers, or (b) a new engine passage that creates a writing spawn and inherits the four isolation duties and the staging window.
- **The scope-ruling, finders, and both re-checkers are judgment roles whose cost of error is rounds, not tokens.** The notebook's cost model (`cost ≈ turns × ~25-33k`) and the "one round is roughly $4–6 of a $18–36 iteration" estimate mean a cheaper judgment role must save more than one extra round's worth to break even; R4's own quality note says "do not tier the judgment roles".
- **`subagent-runs` under-counts, so a tiering effect on the subagent bill will not show in the ledger.** The cost review found the field "2.5× low in the session anchoring the fit" and treats every ledger count as "an intent record" ([cost-review-2026-10-26.md:274](docs/research/cost-review-2026-10-26.md)); transcripts (`tree_cost.py`) are the instrument, not the journal.

### Gaps

- Nothing in the repo records the **effort** any subagent currently runs at: F198 checked models only ("subagent **effort** was not checked here"). Whether finders inherit the parent's `high` or default to the model's own default is unmeasured.
- The repo does not say whether `/security-review` or `/verify` run inline in the parent context or fork; cost review R2 describes `context: fork` skills as a harness feature but does not classify these two.
- No count of finders per round is recorded anywhere I read; the roster record exists per round in `progress.md` (not read here — the ledger is gitignored and not a repo file), so "N per round" could be measured from this repo's own `.claude/loop/` but was not for these notes.

## (B) Where the money goes today, and what the cost research already says about tiering

### Inferences

- **R4's 7–15% is a ceiling on the subagent *token* bill and says nothing about rounds.** With rounds at ~5 per issue and one round ≈ $4–6, a tiering change that adds even one round per issue on average wipes out the whole modeled saving on an $18–36 iteration; the review's own ordering (R1 first, R4 after the benchmark) reflects that.
- **A tiering design must change `stratum.py` or every measurement of it is inadmissible.** Today `group_by_stratum` keys on the parent only; after tiering, two sessions with identical parent strata but different rosters would pool. #281's AC2 ("`stratum.py` groups by roster") is therefore a prerequisite of its AC3, not an afterthought.
- **Pinning in agent frontmatter reaches only the user-global agents (pm, architect, ba); the ad-hoc spawns need the "spawn sentence".** The roles that cost the most subagent context in the hand-check (finders, Explore) have no definition file to pin, so R4's two mechanisms address disjoint role sets.
- **The 0.4.0 era is currently unmeasurable by `engine_cost.py`**, so a tiering PR landing now has no admissible engine-share baseline until `LOAD_TOKENS` gains 0.4.0 rows; `tree_cost.py --sessions` (USD) does not have that dependency.

### Gaps

- No per-role breakdown of the subagent bill exists in the repo: the 33–38% share is a total, and appendix D gives only Explore's share (21M/77M context) for one session. Which roles dominate in a typical session is not stated.
- Subagent **effort** has never been measured (F198 says so explicitly).
- No measurement of a cheaper-model subagent anywhere in the corpus: every priced subagent is `claude-opus-5-5`.

## (C) The exact touch points for new `CAPS` parameters

### Takeaway

A new `CAPS` name has four mandatory touch points (engine/unit or `SKILL.md`; the `/init-loop` §1 binding table; its inference-map row; and this repo's own `loop.config.md`), one test that goes red for a missing skeleton row (`CapsVocabularyTests`), and a set of adjacent tests that go red for the shapes a tiering change is likely to take (a new `agents/` directory or hook script trips `PayloadContentsTests`; a hook not plugin-root-relative trips `PluginIdentifierTests`; `README.md` edits must land in both copies). ## (D) Constraints the maintainer notes impose

### Takeaway

Every design option is bounded by eight standing rules: the engine is project-agnostic and reads config by `CAPS` name only; `SKILL.md` must over-escalate on a partial load; any rule about safe states is written default-deny; a test over prose can pin a coupling's identity but never a claim's truth; wording that lands in the `/init-loop` skeleton is stranded in every consumer config; anything that ships or that the suite runs is stdlib-only; a file ships iff a consumer needs it in the cache; and the loop runs the installed plugin, so no in-tree change takes effect until a release and a re-install.
