# Prior art and evidence: role- and task-based model selection in agentic coding tools

Research notes, compiled 2026-10-31. Every finding carries the page's own date where one is stated; pages marked "fetched 2026-10-31, undated" are live docs that carry no publication date and may have changed since the version a reader consults. Inferences are labeled as such and kept out of the cited lists.

Scope reminder for the report writer: the consumer of this survey is a Claude Code plugin (a supervised dev loop) whose roles are planner/orchestrator, pm/scoping agent, architect reviewer, implementer, code-review finders, a fresh re-check reviewer, an acceptance-criteria verifier, a mutation-test selector, a docs writer, and a test writer. Findings are organized by the assignment's key questions; the plugin-specific inferences sit at the end of each section.

## Key question 1: aider — `--model`, `--editor-model`, `--weak-model`, architect/editor mode

### Takeaway
aider is the clearest precedent for a three-role split in a single-user coding tool: a main (architect) model, an editor model that turns the architect's proposal into file edits, and a "weak" model for commit messages and chat-history summarization. Every secondary role has a provider-derived default keyed off the main model, and the only published benchmark evidence is for the architect/editor pairing, where the win came from separating reasoning from edit formatting rather than from using a cheaper model.

### Cited Findings
- **Three role flags, with help text.** `--model MODEL`: "Specify the model to use for the main chat". `--editor-model EDITOR_MODEL`: "Specify the model to use for editor tasks (default depends on --model)". `--weak-model WEAK_MODEL`: "Specify the model to use for commit messages and chat history summarization (default depends on --model)". Also `--architect` ("Use architect edit format for the main chat"), `--auto-accept-architect` (default True), `--reasoning-effort VALUE` and `--thinking-tokens VALUE` (both "default: not set"). — [aider options reference](https://aider.chat/docs/config/options.html) (fetched 2026-10-31, undated)
- **`.aider.conf.yml` shape** is flat key/value: `model: xxx`, `editor-model: xxx`, `weak-model: xxx`, `architect: false`, `editor-edit-format: xxx`, `reasoning-effort: xxx`, `thinking-tokens: xxx`. — [aider YAML config](https://aider.chat/docs/config/aider_conf.html) (fetched 2026-10-31, undated)
- **`.aider.model.settings.yml`** is a YAML list of per-model entries with fields `name`, `edit_format` (default `whole`), `weak_model_name` (default null), `editor_model_name` (default null), `editor_edit_format`, `use_repo_map`, `reasoning_tag`, `extra_params`; files in home, repo root, and cwd are merged with later files winning. Example entry: `name: fireworks_ai/accounts/fireworks/models/deepseek-r1`, `weak_model_name: .../deepseek-v3`, `editor_model_name: .../deepseek-v3`, `editor_edit_format: editor-diff`. — [aider advanced model settings](https://aider.chat/docs/config/adv-model-settings.html) (fetched 2026-10-31, undated)
- **Shipped defaults pair each main model with a cheaper sibling from the same provider for the weak role, and a same-tier model for the editor role**: `anthropic/claude-sonnet-4-20250514` → weak `anthropic/claude-3-5-haiku-20241022`, editor itself (`editor-diff`); `claude-opus-4-20250514` → weak `claude-3-5-haiku-20241022`, editor `claude-sonnet-4-20250514`; `o3` → weak `gpt-4.1-mini`, editor `gpt-4.1`; `gpt-5` → weak `gpt-5-nano`, no editor set; `gemini/gemini-2.5-pro` → weak `gemini/gemini-2.5-flash`; `openrouter/deepseek/deepseek-r1` → weak and editor `deepseek-chat`. — [aider model-settings.yml (main branch)](https://raw.githubusercontent.com/Aider-AI/aider/main/aider/resources/model-settings.yml) (fetched 2026-10-31)
- **Architect mode mechanics and rationale.** The main model acts "as an architect to propose how to solve your coding request"; a second request asks the editor model to turn that into file edits. aider states the cost plainly: "this uses two LLM requests, which can take longer and increase costs." It is "especially useful" with o1-class models, which are strong at reasoning "but weaker at editing files"; using the same model for both roles can also help because the model gets two passes. — [aider chat modes](https://aider.chat/docs/usage/modes.html) (fetched 2026-10-31, undated; transcript shows v0.47.1-dev)
- **Architect/editor benchmark (2024-09-26), aider code-editing benchmark, pass rate:** o1-preview + o1-mini (whole) 85.0%; o1-preview + deepseek (whole) 85.0%; o1-preview + claude-3-5-sonnet (diff) 82.7%; o1-preview alone 79.7%; claude-3.5-sonnet + itself 80.5% vs 77.4% alone; gpt-4o + itself 75.2% vs 71.4% alone; o1-mini + deepseek (whole) 71.4% vs 61.1% alone; gpt-4o-mini + itself 60.2% vs 55.6% alone. The post calls o1-preview + Sonnet "an entirely practical configuration" and says the 85% whole-format configurations are "probably not practical for interactive use." No cost figures are given. — [Separating code reasoning and editing](https://aider.chat/2024/09/26/architect.html) (2024-09-26)
- **Polyglot leaderboard (last updated 2025-11-20):** gpt-5 (high) 88.0% at $29.08; gpt-5 (medium) 86.7% at $17.69; gpt-5 (low) 81.3% at $10.37; o3 (high) 81.3% at $21.23; **o3 (high) + gpt-4.1 (architect) 78.2% at $17.55**; o3 alone 76.9% at $13.75; DeepSeek R1 + claude-3-5-sonnet (architect) 64.0% at $13.29. The page makes no explicit claim comparing architect pairs to single models. — [aider polyglot leaderboard](https://aider.chat/docs/leaderboards/) (2025-11-20)

### Inferences
- aider's three roles map onto generic categories the plugin can reuse: a *reasoning* role (architect), an *execution* role (editor), and a *bookkeeping* role (weak: commit messages, summaries). The bookkeeping role is the only one aider defaults to a cheaper tier, and it does so without published measurement; the choice is presented as obvious rather than argued.
- The leaderboard rows are the only paired cost data: on the 2025-11-20 board, o3 (high) + gpt-4.1 sits between o3 (high) alone and o3 (default) alone on both score and cost, so by late 2025 the architect split was no longer a free win on frontier models. Meanwhile the gpt-5 low/medium/high rows show effort on one model spanning 81.3%→88.0% at $10.37→$29.08, a wider lever than the architect split.
- aider's "default depends on --model" pattern (derive the secondary roles from the main model, per provider) is the lowest-friction default a user has seen in this space: one setting yields a sensible tiering.

### Gaps
- No aider measurement of the weak model's effect on commit-message or summary quality was found; the rationale is implicit.
- The architect post states no per-configuration cost, so cost-per-pass-rate of the 2024 pairings cannot be reconstructed from it.

## Key question 2: how other tools expose per-role / per-phase model selection

### Takeaway
Across OpenCode, Roo Code, Kilo, Cline, Codex CLI, Continue, Gemini CLI, Cursor, and Copilot, the dominant shape is **a global default plus per-role (or per-mode/agent) override fields**, with secondary roles inheriting from the primary by default; providers can differ per role wherever the override is a full `provider/model` id or a profile. Named presets appear as a *layer above* that (Cursor's Auto modes, Copilot's Auto, Claude Code's `opusplan`), never as the only control. Goose is the cautionary tale: its lead/worker env-var feature was removed within about a year.

### Cited Findings

**OpenCode (opencode.ai)**
- `model` is the main model in `provider/model` format. `small_model` "configures a separate model for lightweight tasks like title generation"; by default "OpenCode tries to use a cheaper model if one is available from your provider", otherwise falls back to the main model. Each `agent.<name>` entry can set its own `model`. Minimal snippet: `{"model": "anthropic/claude-sonnet-5-5", "small_model": "anthropic/claude-haiku-5-5", "agent": {"code-reviewer": {"model": "anthropic/claude-sonnet-5-5"}}}`. — [OpenCode config](https://opencode.ai/docs/config/) (fetched 2026-10-31, undated)
- Built-in agents: Build (primary, all tools), Plan (primary, "restricted agent designed for planning and analysis"), General (subagent), Explore (subagent, "fast, read-only"), plus hidden Compaction/Title/Summary agents. Defaults: "If you don't specify a model, primary agents use the model globally configured"; subagents use the model of the primary agent that invoked them. The docs' own example assigns `plan` → `anthropic/claude-haiku-5-5` and `build`/`code-reviewer` → `anthropic/claude-sonnet-5-5`. Agents can also be markdown files under `.opencode/agents/`. — [OpenCode agents](https://opencode.ai/docs/agents/) (fetched 2026-10-31, undated)

**Goose (block/goose)**
- The 2025-08-11 post "LLM tag team: lead/worker model" is now marked **Outdated** and states: "Lead/Worker mode has been removed from goose, as has the Planning Mode that replaced it." The original design: lead model "handles planning and decision-making", worker "handles execution", with a configurable number of worker turns before the lead is consulted, failure handling, and fallback; rationale was cost and speed, and providers could be mixed. No measured results were reported. — [Goose blog, lead/worker (mirror)](https://goose-docs.ai/blog/2025/08/11/llm-tag-team-lead-worker-model) (2025-08-11, marked Outdated)
- Goose's current configuration guide describes an **experimental AutoPilot** feature for "intelligent, context-aware model switching" configured through an `x-advanced-models` setting in `config.yaml`, with a migration example mapping the old `GOOSE_LEAD_MODEL` setup to a role named `lead`. — reported in search results pointing at [Goose config file guide](https://block.github.io/goose/docs/guides/config-file) and [Goose AutoPilot guide](https://block.github.io/goose/docs/guides/multi-model/autopilot); **direct fetches of both returned 404 on 2026-10-31**, so the schema is unverified (see Gaps).

**Roo Code and Kilo Code**
- "API Configuration Profiles allow you to create and switch between different sets of AI settings." Each profile holds provider, API key, model, temperature, thinking budget, and rate limit. In the Prompts tab you can "explicitly associate a specific Configuration Profile with each Mode", and Roo "automatically remembers the profile you last used with each mode"; a running task keeps the profile it started with. — [Roo Code API configuration profiles](https://roocodeinc.github.io/Roo-Code/features/api-configuration-profiles) (fetched 2026-10-31, undated)
- Built-in modes: Code (default, full tools), Ask (read-only), Architect (read + markdown edits; "Follows a structured approach from information gathering to detailed planning"), Debug (full tools), Orchestrator ("breaks down complex tasks and delegates them to specialized modes"). Guidance is limited to "Assign different models to different modes," with the example of Gemini 2.5 Preview for Architect and Claude Sonnet 3.7 for Code; each mode "remembers your last-used model." No cheaper-for-Ask or stronger-for-Architect recommendation is made. — [Roo Code using modes](https://roocodeinc.github.io/Roo-Code/basic-usage/using-modes) (fetched 2026-10-31, undated)
- Kilo Code (a Roo fork) documents the same mechanism in the same words ("explicitly associate a specific Configuration Profile with each Mode"), per search-result excerpts of [kilo.ai docs](https://kilo.ai/docs/features/api-configuration-profiles); the page itself returned 404 on fetch (2026-10-31).

**Cline**
- Plan mode "cannot modify any files or execute commands"; Act mode "retains the full context from your planning session." A settings toggle "Use different models for Plan and Act" lets you pick a model per mode; Cline switches automatically and the selection persists. The page recommends a stronger reasoning model for planning and a faster model for implementation and gives a use-case table: Cost optimization = GLM 4.6 (Plan) / Grok Code Fast (Act); Maximum quality = Claude Opus / Claude Sonnet; Speed-focused = Gemini 3 Flash / Cerebras. — [Cline plan and act](https://docs.cline.bot/features/plan-and-act) (fetched 2026-10-31, undated)

**Cursor**
- Auto has three modes: **Cost** ("classic Auto", bills as a Cursor-model request from the weekly pool), **Balance**, and **Intelligence** (Teams/Enterprise with Cursor Router; billed at the routed model's list price). "Cursor Router picks among Cursor models and third-party models for each Balance or Intelligence request"; the selection logic is not described. Individual plans get Cost mode only; Plus has no Auto. Max Mode (legacy plans) extends context and bills at API rate plus 20%. Pricing is per million tokens, not multipliers. — [Cursor models and pricing](https://cursor.com/docs/models) (fetched 2026-10-31, undated)

**GitHub Copilot**
- Each prompt in Chat, CLI, Spaces, or to a third-party agent is one premium request "multiplied by the model's rate"; for agentic features "only your prompts count" and tool calls do not. Copilot code review is a flat 13 premium requests per review from 2026-06-01. A Copilot cloud-agent session is one premium request times the model's rate; each steering comment is another. Pro: 300/month at $10; Pro+: 1,500/month at $39; extra requests $0.04. — [Copilot requests](https://docs.github.com/en/copilot/concepts/billing/copilot-requests) (fetched 2026-10-31)
- "On June 1, 2026, GitHub moved to usage-based billing." The legacy annual-plan multiplier table (applies only to Pro/Pro+ annual subscribers who stayed on request-based billing): Claude Haiku 4.5 **0.33**, Claude Sonnet 4.6 **9**, Claude Opus 4.8 **27**, GPT-5.3-Codex **6**, MAI-Code-1.1-Flash **0.25**; code review 13; Auto model selection gives a 10% discount ("a 1x model is billed at 0.9x"). Multipliers are "based on its complexity and resource usage." — [Model multipliers for annual plans (legacy)](https://docs.github.com/en/copilot/reference/copilot-billing/request-based-billing-legacy/model-multipliers-for-annual-plans) (fetched 2026-10-31)
- Auto "chooses from supported models, subject to your policies and subscription type," aiming at "reserving higher-cost reasoning models for problems that truly need it," with a 10% discount on model costs for paid plans in Chat and cloud agent. — [Copilot auto model selection](https://docs.github.com/en/copilot/concepts/auto-model-selection) (fetched 2026-10-31)
- GPT-5.3-Codex "serves as the long-term support model and is used when no other models are available." — [Copilot supported models](https://docs.github.com/en/copilot/reference/ai-models/supported-models) (fetched 2026-10-31)

**OpenAI Codex CLI**
- `config.toml` keys: `model` (string; no default stated), `model_reasoning_effort` (examples `low`, `medium`, `high`, `xhigh`, `max`, `ultra`; "Available levels depend on the model and client"), `model_provider` (default `openai`), `model_providers.<id>` tables (cannot be set in project-local `.codex/config.toml`). **Per-task model keys:** `review_model` ("Model used by `/review`", defaults to "the current session model"), `plan_mode_reasoning_effort`, `agents.default_subagent_model` and `agents.default_subagent_reasoning_effort` (an explicit spawn value takes precedence), `memories.extract_model` and `memories.consolidation_model`. Profiles are separate files `$CODEX_HOME/<name>.config.toml` selected with `--profile <name>`, ranking below CLI flags and project config but above user config. — [Codex config reference](https://learn.chatgpt.com/docs/config-file/config-reference) and [Codex basic config](https://learn.chatgpt.com/docs/config-file/config-basic) (both redirected from developers.openai.com; fetched 2026-10-31, undated)

**Gemini CLI**
- `model.name` sets the conversation model (default unset); `GEMINI_MODEL` and `--model` override. `general.plan.modelRouting` (default `true`): "Automatically switch between Pro and Flash models based on Plan Mode status." An `auto` model entry (`"tier": "auto"`) resolves by default to `gemini-3-pro-preview`. `experimental.gemmaModelRouter.enabled` (default `false`) enables a local Gemma classifier, and `modelConfigs.classifierIdResolutions` holds "Rules for resolving classifier tiers (flash, pro) to concrete model IDs." `agents.overrides` can set "a custom model config" per agent. Internal helpers (`web-search`, `web-fetch`, `next-speaker-checker`) build on a Flash-based alias. — [Gemini CLI configuration reference](https://geminicli.com/docs/reference/configuration.md) (fetched 2026-10-31, undated)

**Continue.dev**
- Each model in `config.yaml` carries a `roles` array drawn from `chat`, `autocomplete`, `embed`, `rerank`, `edit`, `apply`, `summarize` (the last "is not currently used"). If omitted, roles default to `[chat, edit, apply, summarize]`. Different providers per role are the normal case (for example an OpenAI model for chat/edit/apply and a Mistral or Ollama model for autocomplete). — [Continue config reference](https://docs.continue.dev/reference) (fetched 2026-10-31, undated)

### Inferences
- Across all tools the routable roles are of three kinds: (a) **phase** roles (plan vs act; architect vs code; Plan mode vs execution), (b) **agent** roles (OpenCode agents, Codex subagents, Claude Code subagents), and (c) **bookkeeping** roles (aider weak model, OpenCode `small_model`, Codex memory models, Gemini CLI's Flash helpers, Cursor/Copilot title-style tasks). Only the bookkeeping class is routinely defaulted to a cheaper tier by the vendor; phase and agent roles default to *inherit*.
- The configuration idioms that recur, and that users will therefore recognize: a global `model`; a per-role key with the same value syntax (`provider/model`); `inherit` or "defaults to the session model" as the per-role default; and, in tools that need to mix credentials, a named *profile* object that bundles provider + key + model and is then bound per mode.
- Goose's removal of lead/worker (turn-count-based switching) and Cursor's undisclosed router logic both suggest that *automatic* switching inside a session is harder to keep than *static* per-role assignment; every surviving design in this list is static per role or per mode.

### Gaps
- Goose: the exact `x-advanced-models` YAML schema and AutoPilot switching criteria could not be verified (four URL variants returned 404 or empty on 2026-10-31).
- Kilo Code: official page returned 404; the quoted wording comes from search excerpts only.
- Copilot: the current usage-based (post-2026-06-01) price list per model was not retrieved; only the legacy multiplier table was. The coding-agent model-picker page (default model, per-task selection) returned 404.
- Cursor: the per-feature model settings (Tab, Composer, Bugbot) are not documented on the models page retrieved.
- Codex: no stated default `model` or default `model_reasoning_effort` on either page retrieved.

## Key question 3: Anthropic's published guidance on multi-model orchestration and effort

### Takeaway
Anthropic's current docs are explicit and measured: tune effort on one model before adding a second; price the stronger model alone at low effort before building a pairing; delegate to cheaper workers only for bulk work that is independent or larger than one context window; and treat Haiku subagents as "an alternative to lowering effort, not better." Claude Code exposes per-subagent `model` and `effort`, a `CLAUDE_CODE_SUBAGENT_MODEL` default with a `_FORCE` override, `opusplan` as a two-role preset, and the advisor tool as a cheap-executor/strong-advisor pattern.

### Cited Findings

**Patterns and rationale**
- "Building effective agents" (2024-12-19, with later edits): orchestrator-workers is "a central LLM [that] dynamically breaks down tasks, delegates them to worker LLMs, and synthesizes their results," suited to tasks whose subtasks cannot be predicted in advance. Routing example: "Routing easy/common questions to smaller, cost-efficient models like Claude Haiku 4.5" and hard ones to Sonnet 4.5. Agentic systems "often trade latency and cost for better task performance." — [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) (2024-12-19)
- Multi-agent research system (2025-06-13): Opus 4 lead + Sonnet 4 subagents "outperformed single-agent Claude Opus 4 by 90.2% on our internal research eval"; "multi-agent systems use about 15× more tokens than chats"; token usage "explains 80% of the variance" in BrowseComp; viable only where "the value of the task is high enough to pay for the increased performance." — [How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system) (2025-06-13)

**Effort before a second model (the "strongest model at lower effort first" advice)**
- "Tuning effort is often a better lever than switching models." Two starting strategies: efficiency-first (start with Haiku 5.5, upgrade only for capability gaps) and capability-first (start with Opus 5.5, then "Consider increasing efficiency by lowering effort or downgrading models over time"). "Most workloads start with Claude Opus 5.5." Haiku 5.5's row lists "subagent tasks" among its uses. "Multi-model strategies pair a lower-cost model with a frontier model so that most tokens are billed at the lower rate. The two common patterns are an executor that escalates hard decisions to an advisor, and an orchestrator that delegates bulk work to lower-cost workers." — [Choosing the right model](https://platform.claude.com/docs/en/about-claude/models/choosing-a-model) (fetched 2026-10-31, undated)
- "Tune one model before you add a second: sweep effort on your current model first, because most workloads end there, and if the sweep shows a gap, price the stronger model alone at low effort. Build a pairing only if it beats the single model's whole curve of score against spend." "Judge a pairing against the same model at lower effort and against the next model down running alone." — [Optimizing for cost and intelligence](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence) (fetched 2026-10-31, undated)
- Effort sweep, Opus 5.5 on a SWE-bench Pro subset: `low` 87.4% solved at $0.11/task; `medium` (default) 92.8% at $0.21; `high` 95.3% at $0.29; `xhigh` 96.7% (single run) at $0.74. — same page
- Cost-lever table (same page): **Upgrade the model**: "up to 40% less on typical workloads, and up to 87% less per solved task on a coding benchmark", quality "None; a gain on most". **Lower effort**: "On long coding tasks, `medium` cost about 30% to 52% less than `high`, and `low` about two thirds less", quality "Up to 15 points lower, depending on the task". **Re-run failures at higher effort**: "About 40% less than running everything at `high`, at the same pass rate or slightly better". **Advisor**: cost "about 2.1 times the cost of the model alone, on a coding benchmark", quality "a small gain that may be chance; on chart reading, a loss". **Orchestrator**: "About half the cost of the orchestrator's model alone, on work larger than one context window; on routine work, measure first", quality "10 to 12 points lower on that work". — same page
- A tau2-bench retail search from Opus 5 found "Sonnet 5 at low is 61% cheaper within 2 points"; "A second search, started from the lower-cost model at its default effort, kept nothing." The effort and model changes produced the savings; "the prompt edits brought no durable gain." — same page

**Measured multi-model results (same page)**
- Advisor, internal agentic-coding benchmark: Opus 5.5 at `high` + Fable 5.1 advisor scored 90.1%, "1.7 points over the executor alone, at the edge of run-to-run noise", at $2.92/attempt, "about 2.1 times the executor alone", with ~1.4 consults per attempt. GPQA Diamond: Haiku 5.5 or Sonnet 5.5 + Opus 5.5 advisor consulted "None of 198 questions, in two runs each" (cost +12% / +25% for the tool definition). Chartography: Opus 5.5 at `low` + Fable 5.1 advisor scored 7 points *below* the executor alone, consulting 1 of 300 tasks. "An advisor can help only when your model consults it."
- Orchestrator: delegation saved money in two cases, "Routine work with a long cost tail" and "Work larger than one context window"; on a dependent chain or work that fits one context, "the orchestrator's model alone at lower effort came out ahead in every measured case." Defect-search benchmark: orchestrator "costs about half of Fable 5.1 alone at any effort and scores 10 to 12 points below"; "Lowering effort cannot help, because the bill is the reading itself."
- **Haiku 5.5 subagents under Opus 5.5 at `medium` on an internal coding benchmark** (Managed Agents): "cut cost per attempt by 32% and the pass rate by about 4 percentage points (95% interval 1.3 to 7.1)", about what a mix of `low` and `medium` effort without subagents gives at that cost; they were "an alternative to lowering effort, not better."
- Method: "pull production-like tasks, write outcome checks, baseline model tiers across effort levels, add a multi-model strategy only if the single-model curve shows a gap effort can't close, then run the winner in shadow before cutover."

**Effort parameter specifics**
- Levels `low`/`medium`/`high`/`xhigh`/`max`; most models default `high`, Opus 5.5 and Haiku 5.5 default `medium`. `low` is described as "Simpler tasks that need the best speed and lowest costs, such as subagents." "Lower effort also means fewer and terser tool calls." Haiku 5.5 at `low`: "In long agent prompts, the model is more likely to skip a search, stop early, or skip a check at `low`." Haiku 5.5 at `xhigh`/`max`: "compare them with Claude Sonnet 5.5 on performance, cost, and speed." Fable 5: "Lower effort settings on Claude Fable 5 still perform well and often exceed `xhigh` performance on prior models." Opus 4.7: at `max`, "on some structured-output or less intelligence-sensitive tasks it can lead to overthinking." — [Effort](https://platform.claude.com/docs/en/build-with-claude/effort) (fetched 2026-10-31, undated)

**Claude Code and Agent SDK configuration surface**
- Subagent `model` frontmatter accepts `sonnet`, `opus`, `haiku`, `fable`, a full model id, or `inherit`; when omitted, resolution order is: per-invocation `model` parameter → frontmatter `model` → `CLAUDE_CODE_SUBAGENT_MODEL` → the main conversation's model. `CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1` (v2.1.257+) makes the env var override frontmatter. Built-ins: Explore runs on the main model (Opus when main is Fable on Anthropic-API-shaped connections), Plan inherits, `claude-code-guide` runs Haiku, `statusline-setup` Sonnet. Stated purpose: "Control costs by routing tasks to faster, lower-cost models like Haiku"; the one concrete example is overriding Explore with `model: haiku` "to run exploration on a lower-cost model." Subagents inherit the main conversation's thinking configuration (v2.1.198); "There is no per-subagent thinking setting." — [Claude Code subagents](https://code.claude.com/docs/en/sub-agents) (fetched 2026-10-31)
- Agent SDK `AgentDefinition` fields include `model` (alias, `inherit`, or full id; omitted → subagent model order) **and `effort`** (`low`…`max` or a number). The docs' own example gives a `code-reviewer` `model: "sonnet"` and shows a factory that picks `"opus" if is_strict else "sonnet"` with the comment "use a more capable model for high-stakes reviews." Caps: spawn depth default 3, concurrency default 20, `maxBudgetUsd` unbounded by default. — [Subagents in the SDK](https://code.claude.com/docs/en/agent-sdk/subagents) (fetched 2026-10-31)
- Model aliases include `opusplan`: "Special mode that uses `opus` during plan mode, then switches to `sonnet` for execution." Default model is Opus 5.5 on most plans/providers (Sonnet 4.5 on Microsoft Foundry). Effort resolution order: `CLAUDE_CODE_EFFORT_LEVEL` → session pick → `--effort` → saved settings → model default; effort can be set in subagent frontmatter. — [Claude Code model configuration](https://code.claude.com/docs/en/model-config) (fetched 2026-10-31)
- Cost guidance: "Sonnet handles most coding tasks well and costs less than Opus. Reserve Opus for complex architectural decisions or multi-step reasoning." "For simple subagent tasks, specify `model: haiku`." Agent teams: "Use Sonnet for teammates"; teams "use approximately 7x more tokens than standard sessions when teammates run in plan mode." Enterprise average "around $13 per developer per active day and $150-250 per developer per month." — [Manage costs effectively](https://code.claude.com/docs/en/costs) (fetched 2026-10-31)
- Advisor tool (experimental, Anthropic API only): "Pair your main model with a stronger advisor model that Claude consults at key moments"; an advisor must rank at or above the main model (Haiku 4.5 can call but not act as one). Pairing table includes "Haiku main + Opus advisor: Lowest-cost main model with strong planning. Expect higher cost than Haiku alone but lower than switching the main model to Sonnet or Opus" and "Opus main + Opus advisor: A second Opus reviews the first." "It adds less value on short tasks where there is little to plan, or on work where every turn needs the strongest model. For those, switch the main model instead." Comparison table: advisor (at decision points) vs `opusplan` (plan mode only) vs subagents with `model` (entire delegated subtask) vs `/model`. — [Escalate hard decisions with the advisor tool](https://code.claude.com/docs/en/advisor) (fetched 2026-10-31)

### Inferences
- Anthropic's position, read across these pages, is a decision procedure rather than a tiering recommendation: (1) one model, sweep effort; (2) if quality is short, price the next model up at low effort; (3) only then pair models, and only for roles whose work is independent or oversized. For a dev-loop plugin, that argues for shipping a default where every role inherits the session model and effort is the first per-role knob, with cheaper-tier overrides as an opt-in for bulk, read-only roles.
- The Haiku-subagent measurement (-32% cost, -4 points) is the closest thing to a controlled result for "cheap worker under a strong orchestrator" on coding work, and it was judged no better than lowering effort on the orchestrator alone. The plugin's analogous roles are the mutation-test selector, docs writer, and read-only exploration inside reviewers.
- The advisor results (zero consults on GPQA; 1 of 300 on Chartography; a 7-point loss) show that an escalation design fails silently when the weak executor does not escalate. The plugin's supervised gates (human approval, AC verifier) are a structural substitute for that escalation, which is an argument that the *gate* roles are where a cheaper model is riskiest.

### Gaps
- No Anthropic engineering post devoted specifically to "use Haiku for subagents" was found; the guidance lives in the docs pages cited above and in the Haiku 4.5 announcement (Sonnet 4.5 orchestrating "a team of multiple Haiku 4.5s").
- The internal benchmarks behind the lever table (agentic-coding, defect-search, Chartography) are not public, so the numbers cannot be reproduced.

## Key question 4: LLM routing research (RouteLLM, FrugalGPT, cascades, Hybrid LLM, Not Diamond, Martian)

### Takeaway
The routing literature shows large cost reductions (35–98%) on single-turn benchmarks while retaining most of the strong model's quality, but every result is on chat/QA/math prompts with a learned per-query router, not on multi-turn tool-use workloads; the one agentic measurement found (Arize/Fireworks, July 2026) shows cost-per-successful-task diverging sharply from per-token price and a cheap-first escalation ladder beating the best single model on both cost and coverage.

### Cited Findings
- **RouteLLM** (LMSYS; arXiv 2406.18665, v1 2024-06-26, v4 2025-02-23): routers trained on human preference data "dynamically select between a stronger and a weaker LLM during inference," cutting cost "by over 2 times in certain cases" without compromising quality, and transferring when the model pair changes. — [RouteLLM abstract](https://arxiv.org/abs/2406.18665)
- RouteLLM blog (2024-07-01): versus GPT-4 alone, cost reductions of "over 85%" on MT Bench, ~45% on MMLU, ~35% on GSM8K "while still achieving 95% of GPT-4's performance"; matched Martian and Unify on MT Bench "while being over 40% cheaper." Strong/weak pair: GPT-4 Turbo / Mixtral 8x7B. Limitations stated: routers trained only on Chatbot Arena data were near random on MMLU until augmented with MMLU golden labels (out-of-distribution); the setup covers two models; generalization to new pairs shown only on MT Bench; Mixtral calls treated as negligible cost. — [RouteLLM blog](https://lmsys.org/blog/2024-07-01-routellm/) (2024-07-01)
- **FrugalGPT** (Chen, Zaharia, Zou; arXiv 2305.05176, 2023-05-09): LLM API prices "differ by two orders of magnitude"; an LLM cascade "can match the performance of the best individual LLM (e.g. GPT-4) with up to 98% cost reduction or improve the accuracy over GPT-4 by 4% with the same cost." Three strategies: prompt adaptation, LLM approximation, LLM cascade. — [FrugalGPT abstract](https://arxiv.org/abs/2305.05176)
- **Hybrid LLM** (Ding et al., ICLR 2024; arXiv 2404.14618, 2024-04-22): a router assigns queries to a small or large model by predicted difficulty and a tunable quality level; "up to 40% fewer calls to the large model with no drop in response quality." — [Hybrid LLM abstract](https://arxiv.org/abs/2404.14618)
- **RouterBench** (Hu et al.; arXiv 2403.12031, 2024-03-18; code under the `withmartian` GitHub org): an evaluation framework for routers with "over 405k inference outcomes," motivated by the claim that no single LLM is best "particularly when balancing performance with cost." — [RouterBench abstract](https://arxiv.org/abs/2403.12031)
- **Not Diamond**: its docs describe "an intelligent multi-model AI infrastructure platform" that predicts "which LLM is best suited to each input"; the benchmark page could not be fetched (404). Search excerpts attribute to it a claim that routing on MMLU beats GPT-4o "while lowering cost by nearly 30%" and an acknowledgment that benchmarks are "weakly correlated with real-world performance" — **unverified**. — [Not Diamond docs index](https://docs.notdiamond.ai/docs) (fetched 2026-10-31)
- **Cost per successful task on agent tasks** (Arize AI with Fireworks, July 2026): 10 models, 40 Terminal-Bench tasks, 6 trials each (2,400 runs, ~$626). Metric: total spend across all attempts including failures and timeouts, divided by successes. gpt-oss-120b was cheapest per success ($0.054) but passed only 33%; GPT-5.5 $0.636 at 67% and Kimi K3 $0.670 at 66%; gemini-3.5-flash $1.233 per success at 23% with 91% of failures from the token cap; Claude Sonnet 5 $1.014 (49%). An escalation ladder (cheap model first, stronger on failure) cost $0.525 per success and solved ~32.3/40 tasks vs GPT-5.5 alone at $0.636 and 25/40; naively escalating through all 10 models cost $1.319. "Paying frontier prices bought little on easy tasks, while the hardest tasks required frontier-class models." Results are "directional" (±6 points). — [Cost per successful task](https://arize.com/?p=30247) (July 2026)

### Inferences
- The routing papers' cost figures are not transferable to a dev loop: they route one prompt at a time against a reference answer, treat the weak model as near-free, and evaluate on distributions (MT Bench, MMLU, GSM8K) far from multi-step tool use. RouteLLM's own MMLU failure without in-distribution data is the warning: a router needs labeled data from the target workload.
- What does transfer is the *cascade/escalation* shape: try cheap, verify, escalate on failure. Arize's ladder beating GPT-5.5 alone, and Anthropic's "re-run failures at higher effort" lever (~40% less at the same pass rate), are two independent measurements of the same idea on agentic tasks. In the plugin, the existing gates (tests, AC verifier, review rounds) already supply the verification step that a cascade needs.
- The Arize numbers also show the failure mode the assignment asked about: a cheap model whose failures are token-cap timeouts (gemini-3.5-flash) costs more per success than a frontier model.

### Gaps
- No Martian cost/quality figures from a primary Martian source were found; only RouterBench (which Martian's org hosts) was retrieved.
- Not Diamond's benchmark page returned 404; its claims above are from search excerpts.
- No routing paper evaluated on SWE-bench-style or tool-use workloads was found in this search.

## Key question 5: evidence that specific SE sub-tasks tolerate cheaper models

### Takeaway
Tier gaps on agentic coding benchmarks are consistent and moderate (Haiku 4.5 trails Sonnet 4.5 by ~4 points on SWE-bench Verified, 73.3 vs 77.2, and Opus 4.5 by ~6 on SWE-bench Pro public, 39.45 vs 45.89), while effort on one strong model spans a wider range than the tier gap (Opus 5.5 low→xhigh: 87.4→96.7 on a SWE-bench Pro subset). For review/judging roles the literature says single-model judges are "uneven" and systematically over-reject correct code; for test generation one 2025 study finds small open models competitive on mutation score; for commit messages and summaries the only evidence is that every vendor defaults those roles to the cheap tier without publishing a measurement.

### Cited Findings

**Benchmark scores by tier (with dates)**
- Claude Haiku 4.5 (2025-10-15): $1/$5 per million tokens; SWE-bench Verified **73.3%** (50-trial average); Terminal-Bench 40.21% without thinking, 41.75% with a 32K thinking budget; "at one-third the cost and more than twice the speed" of Sonnet 4; positioned for Sonnet 4.5 to orchestrate "a team of multiple Haiku 4.5s to complete subtasks in parallel." — [Introducing Claude Haiku 4.5](https://www.anthropic.com/news/claude-haiku-4-5) (2025-10-15)
- Claude Sonnet 4.5 (2025-09-29): $3/$15; SWE-bench Verified **77.2%** (10-trial average; 78.2% at 1M context; 82.0% high-compute); OSWorld 61.4%. — [Introducing Claude Sonnet 4.5](https://www.anthropic.com/news/claude-sonnet-4-5) (2025-09-29)
- Claude Opus 4.5 (2025-11-24): $5/$25; "at medium effort, Opus 4.5 matches Sonnet 4.5's best score on SWE-bench Verified, but uses 76% fewer output tokens"; at highest effort it "exceeds Sonnet 4.5 by 4.3 percentage points while using 48% fewer tokens"; Warp reports "a 15% improvement over Sonnet 4.5" on Terminal Bench. The numeric SWE-bench Verified score appears only in a chart image. — [Introducing Claude Opus 4.5](https://www.anthropic.com/news/claude-opus-4-5) (2025-11-24)
- SWE-bench Pro public leaderboard (Scale AI; 731 public tasks from 1,865 total; uncapped runs have a 250-turn limit, capped runs 50 turns; page undated, 2026 copyright): claude-opus-4-5-20251101 **45.89 ±3.60**; claude-4-5-Sonnet **43.60 ±3.60**; claude-4-Sonnet 42.70; gpt-5-2025-08-07 (High) 41.78; gpt-5.2-codex 41.04; claude-4-5-haiku **39.45 ±3.55**; gemini-3-flash 34.63; gpt-5.2 29.94; gpt-oss-120b 16.20. No benchmark scores are on the page. — [What's new in Claude Haiku 5.5](https://platform.claude.com/docs/en/models/haiku-5-5/whats-new-haiku-5-5) (fetched 2026-10-31)
- aider polyglot (2025-11-20): gpt-5 at low/medium/high effort scored 81.3% / 86.7% / 88.0% at $10.37 / $17.69 / $29.08. — [aider leaderboard](https://aider.chat/docs/leaderboards/)
- Anthropic effort sweep, Opus 5.5 on a SWE-bench Pro subset: low 87.4% ($0.11) → xhigh 96.7% ($0.74). — [Optimizing for cost and intelligence](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)

**Code review / bug finding**
- Cihan, İçöz, Haratian, Tüzün, "Evaluating Large Language Models for Code Review" (arXiv 2505.20206, 2025-05-26): on 492 AI-generated code blocks with problem descriptions, GPT-4o classified correctness at 68.50% vs Gemini 2.0 Flash 63.89%, and corrected code 67.83% vs 54.26%; performance dropped without problem descriptions; the authors propose a human-in-the-loop review process because of the "risk of faulty outputs." (A secondary summary in search results attributes false-positive rates of 14.47% vs 21.71% to the paper; the abstract does not state them — unverified.) — [arXiv 2505.20206](https://arxiv.org/abs/2505.20206)
- Jin and Chen, "Are LLMs Reliable Code Reviewers? Systematic Overcorrection in Requirement Conformance Judgement" (arXiv 2603.00539, 2026-02-28): "LLMs frequently misclassify correct code implementation as non-compliant or defective," and more detailed prompts, "especially those requiring explanations and proposed corrections," raise misjudgment rates. — [arXiv 2603.00539](https://arxiv.org/abs/2603.00539)
- Ullah and Serwadda, "Vibe Coding on Trial: Operating Characteristics of Unanimous LLM Juries" (arXiv 2602.18492, v1 2026-02-12, v2 2026-08-22): 15 open models on 82 text-to-SQL tasks; "single-model judges are uneven"; "small unanimous committees of strong models can cut false accepts" while passing many good queries; "The exact committee composition matters significantly." — [arXiv 2602.18492](https://arxiv.org/abs/2602.18492)
- Anthropic's advisor measurements (above): a strong second model consulted at the weak model's discretion was consulted 0/198 (GPQA) and 1/300 (Chartography) times, and the Chartography pairing scored 7 points below the executor alone. — [Optimizing for cost and intelligence](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)

**Commit messages, summaries, titles, docs**
- aider routes "commit messages and chat history summarization" to the weak model, defaulting to Haiku 3.5 / gpt-4.1-mini / gpt-5-nano / Gemini 2.5 Flash depending on the main model. — [aider options](https://aider.chat/docs/config/options.html); [model-settings.yml](https://raw.githubusercontent.com/Aider-AI/aider/main/aider/resources/model-settings.yml)

**Cheaper model → more retries → higher cost per completed task**

- Arize/Fireworks: gemini-3.5-flash at $1.233 per success (23% pass, 91% of failures hit the token cap) cost more per completed task than GPT-5.5 at $0.636 (67%). — [Cost per successful task](https://arize.com/?p=30247) (July 2026)
- Community report in the oh-my-opencode-slim preset thread: a cheaper OpenAI model ("Luna") failed `apply_patch` "about 44% of the time per 100 calls, versus under 10% for Terra," prompting a proposal to move the `fixer` role default to the stronger model. — [oh-my-opencode-slim discussion #751](https://github.com/alvinunreal/oh-my-opencode-slim/discussions/751) (2026-07-12 to 2026-10-27)

### Inferences
- Role-by-role, the evidence supports this ordering of "safe to cheapen": bookkeeping (commit messages, summaries, titles) — universal vendor practice, no counter-evidence; read-only exploration/bulk reading — Anthropic's measured orchestrator wins; test generation — mixed, with one study finding small models competitive on mutation score but older work finding invalid-syntax problems; implementer — a measurable tier gap (SWE-bench Pro 39.5 → 45.9) that effort on the stronger model can exceed in the other direction; review/judging — the weakest case, where "uneven" judges and systematic over-rejection make a cheap finder a false-positive generator for the human gate rather than a cost saving.
- A "fresh re-check reviewer" or AC verifier whose purpose is to catch what the implementer missed is structurally the role where over-rejection (false negatives on correct code, per Jin and Chen) is least harmful and false acceptance most harmful — which favors the strong tier, or a unanimous committee of strong models per Ullah and Serwadda, over a single cheap model.
- The tokenizer change on Haiku 5.5 (+~30% tokens) narrows its per-task price advantage relative to its list price; price comparisons across tiers should be done per solved task, as both Anthropic and Arize do.

### Gaps
- No study was found that isolates model *tier within one family* as the variable for code-review false-positive rates; the two-model comparison (GPT-4o vs Gemini 2.0 Flash) conflates vendor and size.
- No published measurement of cheap-model quality for commit messages, PR descriptions, or documentation prose was found; the practice is universal but unargued.
- Terminal-Bench: the tbench.ai leaderboard is JavaScript-rendered (now "Terminal-Bench 4.0") and returned no rows; only vendor-reported Terminal-Bench numbers are cited.
- Opus 4.5's numeric SWE-bench Verified score is in a chart image on the announcement, not in text.
- Nothing was found on model-tier effects for mutation-test selection specifically.

## Key question 6: how tools present the choice — named profiles/tiers vs per-role fields

### Takeaway
Shipping products expose **per-role fields** as the primitive and add **named presets** on top (Cursor's Auto Cost/Balance/Intelligence, Copilot's Auto with a 10% discount, Claude Code's `opusplan`, Cline's cost/quality/speed example table); community plugins in the Claude Code and OpenCode ecosystems converge on a *profile table* (quality / balanced / budget) that fills a per-agent matrix, with per-agent overrides winning. No quantitative adoption data for either presentation was found; the friction users name is choosing models per role across providers, which presets exist to remove.

### Cited Findings
- Cursor's Auto is presented as three named optimization modes, Cost, Balance, Intelligence, with routing logic undisclosed and availability gated by plan. — [Cursor models](https://cursor.com/docs/models) (fetched 2026-10-31)
- Copilot's Auto is a single toggle with a stated goal ("reserving higher-cost reasoning models for problems that truly need it") and a 10% price discount as the adoption incentive. — [Copilot auto model selection](https://docs.github.com/en/copilot/concepts/auto-model-selection) (fetched 2026-10-31)
- Claude Code's `opusplan` alias is a two-role preset ("`opus` during plan mode, then switches to `sonnet` for execution") offered alongside per-subagent `model` fields and a global `CLAUDE_CODE_SUBAGENT_MODEL` default. — [Claude Code model configuration](https://code.claude.com/docs/en/model-config); [Claude Code subagents](https://code.claude.com/docs/en/sub-agents)
- Cline exposes two per-mode fields and documents them with a three-row preset table (Cost optimization / Maximum quality / Speed-focused). — [Cline plan and act](https://docs.cline.bot/features/plan-and-act)
- Roo Code and Kilo bind a named *profile* (provider + key + model + sampling settings) to each mode, with last-used-per-mode memory as the default behavior. — [Roo Code API configuration profiles](https://roocodeinc.github.io/Roo-Code/features/api-configuration-profiles)
- Codex uses per-task keys (`review_model`, `agents.default_subagent_model`, `plan_mode_reasoning_effort`) plus file-based profiles selected with `--profile`, recommending shared defaults in `config.toml` and profile files "only for values that differ." — [Codex config reference](https://learn.chatgpt.com/docs/config-file/config-reference); [Codex basic config](https://learn.chatgpt.com/docs/config-file/config-basic)
- **gsd-hermes (a Claude Code workflow package) "Model Profiles":** profiles `quality`, `balanced` (default, "Smart allocation"), `budget`, `adaptive`, `inherit`, each a column in a 12-agent table. `balanced` = Opus only for the planner, Sonnet for roadmapper/executor/researchers/debugger/verifier/checkers, Haiku for the codebase mapper; `budget` = Sonnet for planner and writing agents, Haiku for most research/verification/checking; rationale notes include "Verifiers in balanced: Haiku may miss subtle gaps" and "Executors follow explicit PLAN.md instructions." Resolution order: `model_overrides[<agent>]` → dynamic-routing tier → `models[<phase_type>]` → the profile table. `inherit` exists because "Organizations may block older opus versions while allowing newer ones." — [gsd-hermes model-profiles.md](https://cdn.jsdelivr.net/npm/gsd-hermes@1.16.0/get-shit-done/references/model-profiles.md) (package v1.16.0; fetched 2026-10-31)
- **oh-my-opencode-slim preset thread** (2026-07-12 to 2026-10-27): roles are orchestrator, oracle, council, designer, explorer, librarian, fixer, observer; users share named presets ("thirtydollars", "gpt&go", a flat Atlas preset with one model everywhere) mixing pay-as-you-go, subscription, and free tiers because "cheap and fast is fine" for librarian/fixer. On friction: "I think it could require some research to find optimal models so that could be one friction"; presets "should" list required providers up front. The thread did not settle whether provider mixing is worth the configuration. — [oh-my-opencode-slim discussion #751](https://github.com/alvinunreal/oh-my-opencode-slim/discussions/751)
- Search excerpts (not fetched): pan-wizard's model-profiles doc uses the same profile-plus-override ladder with `balanced` as default and a complexity score that can step a tier up; Prospector Studio describes tiers as "a default, not a cage." — search results only, unverified

### Inferences
- The convergent design in the plugin ecosystem is a two-layer scheme: a **profile** name that fills a per-role matrix, and **per-role overrides** that win. That is familiar to users of both Claude Code (`opusplan` + subagent `model`) and OpenCode (`model` + per-agent `model`), and it maps directly onto the plugin's `CAPS` binding vocabulary: one `MODEL_PROFILE`-style value with per-role `MODEL_<ROLE>` keys defaulting to `inherit`.
- `inherit` as the universal default (OpenCode, Claude Code, Codex `review_model`) is the fail-safe choice for a supervised loop: an unset binding degrades to "same model as the orchestrator," never to a cheaper tier, which matches this repo's default-deny posture for unknown states.
- The adoption signal, such as it is, favors presets for discovery and per-role fields for retention: every community preset thread is users asking which model to put in which role, and every shipped preset (Cursor, Copilot, opusplan) is a vendor collapsing that question to one choice.

### Gaps
- No survey, telemetry, or vendor statement comparing adoption of named tiers vs per-role configuration was found; the evidence is anecdotal thread activity.
- Cursor's and Copilot's router logic (what "Balance" or "Auto" actually picks) is undisclosed, so their presets cannot be treated as evidence about which roles tolerate cheaper models.
