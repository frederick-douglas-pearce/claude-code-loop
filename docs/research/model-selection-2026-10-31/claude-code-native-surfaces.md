# Claude Code native model and effort selection surfaces (as of 2026-10-31)

**Scope.** Every native mechanism Claude Code (the CLI) offers for choosing which model and which
effort level a piece of work runs on, for the main session and for subagents spawned with the Agent
tool. Intended input for designing per-role model selection inside a plugin whose orchestrator runs
in the main session and spawns subagents for review, verification, planning, and scoping.

**Sources and their dates.** All `code.claude.com/docs/en/...` pages were fetched 2026-10-31. None
shows a "last updated" date; each carries version notes, the newest being v2.1.311 (model-config,
`ultrathink`) and v2.1.310 (plugins/components, monitors). The `anthropics/claude-code` CHANGELOG was
fetched raw 2026-10-31; its top heading is `## 2.1.316`, undated. Local checks were run on this
machine the same day: `claude --version` reports **2.1.316**; the session running this research
executes from `~/.local/share/claude/versions/2.1.314` (`CLAUDE_CODE_EXECPATH`), so the Agent tool
schema quoted below is 2.1.314's. Support-center articles show only "Updated today", so their
revision date is unknown.

**Labels.** "Verified" = stated on an official page cited inline. "CHANGELOG-only" = stated in the
GitHub changelog but not yet on any doc page. "Local" = observed on this machine. "Inference" is
listed separately in each section and is never cited as fact.

## Q1. Main-session model selection: `model` setting, `/model`, `--model`, `ANTHROPIC_MODEL`, `ANTHROPIC_DEFAULT_*_MODEL`, `ANTHROPIC_SMALL_FAST_MODEL`, `opusplan`, `[1m]`

### Takeaway
Nine aliases exist (`default`, `best`, `fable`, `sonnet`, `opus`, `haiku`, `sonnet[1m]`, `opus[1m]`,
`opusplan`), full model IDs are accepted everywhere an alias is, and the documented priority for the
main session is `/model` > `--model` > `ANTHROPIC_MODEL` > settings `model` > `ANTHROPIC_DEFAULT_MODEL`.
`ANTHROPIC_SMALL_FAST_MODEL` is deprecated in favor of `ANTHROPIC_DEFAULT_HAIKU_MODEL`.

### Inferences
- For a plugin, the only main-session model surfaces it can legitimately ship are an `agent` default in its `settings.json` (lowest layer, user-overridable) and advisory text; everything else (`/model`, `--model`, `ANTHROPIC_MODEL`, user/project `model`) is the user's. A plugin cannot pin the orchestrator's model without the user cooperating.
- `ANTHROPIC_DEFAULT_*_MODEL` are the right hook for *provider-portable* alias pinning (they are read for subagent `model:` aliases too, see Q3), but they are user/org environment, not plugin payload.

### Gaps
- The docs do not state where a `--agents`-defined agent's `model` sits relative to the `agent` setting when both name the main-session agent; only the location priority for *name collisions* is documented (Q2).

## Q2. Subagent definitions: locations, priority, and the full frontmatter (what `model:` and `effort:` accept, defaults, other cost-relevant fields)

### Takeaway
`model:` accepts `sonnet` / `opus` / `haiku` / `fable`, any full model ID (same values as `--model`), or `inherit`; when omitted the subagent follows the four-step model order in Q3 (so it ends on the main model unless `CLAUDE_CODE_SUBAGENT_MODEL` is set). `effort:` accepts `low` / `medium` / `high` / `xhigh` / `max`, overrides the session effort, and loses only to `CLAUDE_CODE_EFFORT_LEVEL`. Plugin agents support both fields but drop `permissionMode`, `hooks`, `mcpServers`, `initialPrompt`.

### Cited Findings
- Locations and priority: "Managed settings | Organization-wide | 1 (highest)"; "`--agents` CLI flag | Current session | 2"; "`.claude/agents/` | Current project | 3"; "`~/.claude/agents/` | All your projects | 4"; "Plugin's `agents/` directory | Where plugin is enabled | 5 (lowest)". "When names collide, the higher-priority location wins." Directories are scanned recursively; identity comes only from `name`; nested `.claude/agents/` closest to the working directory wins — [sub-agents](https://code.claude.com/docs/en/sub-agents)
- Frontmatter `model` row, verbatim: "Model to use: `sonnet`, `opus`, `haiku`, `fable`, a full model ID such as `claude-opus-5-5`, or `inherit`. When you omit it, Claude Code picks the model in the subagent model order" — [sub-agents](https://code.claude.com/docs/en/sub-agents)
- "Choose a model" bullets: "**Full model ID**: use a full model ID such as `claude-opus-5-5` or `claude-sonnet-5`. Accepts the same values as the `--model` flag"; "**inherit**: use the same model as the main conversation" — [sub-agents](https://code.claude.com/docs/en/sub-agents)
- Frontmatter `effort` row, verbatim: "Effort level when this subagent is active. Overrides the session effort level, but not the `CLAUDE_CODE_EFFORT_LEVEL` environment variable. Options: `low`, `medium`, `high`, `xhigh`, `max`; available levels depend on the model." — [sub-agents](https://code.claude.com/docs/en/sub-agents)
- Model-config confirms: "Skill and subagent frontmatter: `effort` overrides the level while that skill or subagent runs." — [model-config](https://code.claude.com/docs/en/model-config)
- Only `name` and `description` are required; "Field names are camelCase and must match exactly, because unrecognized fields are ignored without an error." — [sub-agents](https://code.claude.com/docs/en/sub-agents)
- Other cost-relevant fields: `tools` (inherits every tool available to subagents if omitted); `disallowedTools`; `permissionMode` (`default`, `acceptEdits`, `auto`, `dontAsk`, `bypassPermissions`, `plan`, `manual`; "Ignored for plugin subagents"); `maxTurns` ("At the limit, output is returned marked as partial, and Claude can resume the subagent"); `autoCompactWindow` (100000–1000000; v2.1.296+; write a plain integer, `200k` reads as 200); `skills` (full content preloaded); `mcpServers`, `hooks` (ignored for plugin subagents); `memory` (`user`/`project`/`local`); `background` (`true` keeps it in the background even when Claude asks to wait); `omitClaudeMd` (v2.1.271+); `isolation: worktree` (branched from the default branch, auto-cleaned if no changes); `color`; `initialPrompt` (main-session agent only; ignored for plugin subagents); `experimental.cacheTtl` (`5m` or `1h`; v2.1.248+) — [sub-agents](https://code.claude.com/docs/en/sub-agents)
- Plugin agents: "Supported fields: `name`, `description`, `model`, `effort`, `maxTurns`, `autoCompactWindow`, `tools`, `disallowedTools`, `skills`, `memory`, `background`, `omitClaudeMd`, `isolation`, `color`, and the `cacheTtl` key of `experimental`. The only valid `isolation` value is `"worktree"`." "Ignored fields: `permissionMode`, `hooks`, `mcpServers`, and `initialPrompt`." Name form `<plugin>:<name>`, subfolders join with colons; the `agents` manifest key replaces the `agents/` scan and must list `.md` files (directories not accepted). Frontmatter that doesn't parse still loads with every field ignored — [plugins/components](https://code.claude.com/docs/en/plugins/components), [plugins/manifest-reference](https://code.claude.com/docs/en/plugins/manifest-reference)
- `--agents` JSON takes `prompt` plus the frontmatter fields (e.g. `"model": "sonnet"`), ignoring `color` and `experimental`; in `-p` mode it also accepts a path to a JSON file — [sub-agents](https://code.claude.com/docs/en/sub-agents)
- Startup context of a non-fork subagent: its own system prompt (not Claude Code's), the delegation message, the full CLAUDE.md hierarchy (unless `omitClaudeMd`, or Explore/Plan), git status snapshot, preloaded skills, sibling roster. "The subagent's window is sized by its own model." Output style, auto memory, and the parent's context window size never reach it — [sub-agents](https://code.claude.com/docs/en/sub-agents)
- Cost knobs: "Keep `description` fields brief. Claude Code warns at startup when the combined descriptions of non-built-in subagents exceed 15,000 tokens"; `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` default 20 (v2.1.217+); `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` default 3 (v2.1.219+, was 1 in 2.1.217–218) — [sub-agents](https://code.claude.com/docs/en/sub-agents), [env-vars](https://code.claude.com/docs/en/env-vars)
- Background subagents run with a smaller built-in tool set (Read, Grep, Glob, LSP, Bash, PowerShell, Edit, Write, NotebookEdit, WebFetch, WebSearch, TodoWrite, Skill, ToolSearch, EnterWorktree, ExitWorktree, Monitor, TaskStop, SendMessage, Artifact; MCP tools kept); "Subagents that Claude spawns from the main conversation start in the background by default, unless fork mode is on and Claude is waiting" — [sub-agents](https://code.claude.com/docs/en/sub-agents)
- Local: `~/.claude/agents/architect.md`, `pm.md`, `ba.md` carry `model: claude-opus-5-5` (a full ID); `marketer.md` carries `model: sonnet`; none sets `effort:`. The installed `dev-loop` plugin ships no `agents/` directory and no `model:`/`effort:` frontmatter anywhere under `plugins/dev-loop/`.
- CHANGELOG 2.1.267: "Fixed `effort:` frontmatter on custom commands, skills, and subagents being ignored on models whose default effort is still pinned (Opus 4.7, Opus 4.8, Fable 5)"; 2.1.0 "Fixed subagents sometimes not inheriting the parent's model by default" — [CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)

### Inferences
- A plugin that wants per-role models must ship its own `agents/*.md` with `model:` set; a user-level agent of the same name (priority 4) would shadow it, so plugin agent names should be distinctive (they are namespaced `plugin:name`, which also avoids collisions).
- Because unrecognized frontmatter is silently ignored, a typo such as `Model:` or `effort_level:` yields no error and the subagent silently runs on the inherited model/effort. A test that parses plugin agent frontmatter against the supported-field list would catch this.

### Gaps
- No doc states a default value for `effort:` beyond "comes from the effort resolution order"; the resolution order is session-level (Q4), and 2.1.316's `CLAUDE_CODE_SUBAGENT_EFFORT` changes what "inherit" means (Q4, CHANGELOG-only).

## Q3. The Agent tool's own `model` / `effort` parameters versus the definition's frontmatter: which wins, and what the caller can pass

### Takeaway
Per-invocation `model` on the Agent call beats the definition's `model:` frontmatter, which beats `CLAUDE_CODE_SUBAGENT_MODEL`, which beats the main model; the caller can pass only an alias (`sonnet`/`opus`/`haiku`/`fable`), never a full ID or `inherit`. Per-invocation `effort` (v2.1.292+) beats frontmatter `effort:` and persists on resume; both lose to `CLAUDE_CODE_EFFORT_LEVEL`. `CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1` disables both model overrides. Forks ignore both parameters.

### Cited Findings
- Verbatim: "When Claude invokes a subagent, it can also pass a `model` parameter for that specific invocation. On an Agent tool call, that parameter takes a model alias: `sonnet`, `opus`, `haiku`, or `fable`. Claude can't pass a full model ID or `inherit` on that call. Claude Code resolves the subagent's model in this order: 1. The per-invocation `model` parameter 2. The subagent definition's `model` frontmatter, where `inherit` selects the main conversation's model 3. The `CLAUDE_CODE_SUBAGENT_MODEL` environment variable, when you set it to a model alias or model ID 4. The main conversation's model" — [sub-agents](https://code.claude.com/docs/en/sub-agents)
- "If an installed mod sets a model in its `agent.spawn` hook, Claude Code uses that model in place of the per-invocation parameter." — [sub-agents](https://code.claude.com/docs/en/sub-agents)
- Family-alias quirk, verbatim: "In two cases, a family alias such as `opus` in the per-invocation parameter or the frontmatter resolves to the main conversation's model instead of the version the alias points to: The main conversation's model belongs to that family: the subagent runs on the main conversation's exact model, including any `[1m]` suffix ... Claude Code can't tell the main conversation's model family, on a provider other than the Anthropic API ... This case covers only the `opus` alias, and doesn't apply when you set `ANTHROPIC_DEFAULT_OPUS_MODEL`". "An alias in `CLAUDE_CODE_SUBAGENT_MODEL` always resolves to the version the alias points to, even when it names the main conversation's family. Setting the variable to `inherit` is the same as leaving it unset." — [sub-agents](https://code.claude.com/docs/en/sub-agents)
- Superseded behavior: "Before v2.1.251, `CLAUDE_CODE_SUBAGENT_MODEL` came first in this order and overrode both the per-invocation parameter and the frontmatter, including `model: inherit`." — [sub-agents](https://code.claude.com/docs/en/sub-agents); CHANGELOG 2.1.251: "Changed `CLAUDE_CODE_SUBAGENT_MODEL` to set the default subagent model rather than override everything: an agent definition's `model:` and an explicit per-spawn model now take precedence over it" — [CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)
- Env-vars row, verbatim: "`CLAUDE_CODE_SUBAGENT_MODEL` | The default model for subagents, agent team teammates, and workflow agents that aren't assigned a model another way. Accepts an alias such as `haiku` or a full model name. Two sources take precedence over it: a model Claude passes when it spawns the agent, and a `model` field in the agent's definition, including `inherit`. To change that, set `CLAUDE_CODE_SUBAGENT_MODEL_FORCE`. ... Setting it to `inherit` is the same as leaving it unset. Before v2.1.251, this variable overrode both the per-invocation model and the definition's `model` field" — [env-vars](https://code.claude.com/docs/en/env-vars)
- Force mode: "`CLAUDE_CODE_SUBAGENT_MODEL` is a default ... To apply one model to every subagent, teammate, and workflow agent, also set `CLAUDE_CODE_SUBAGENT_MODEL_FORCE` to `1`. Requires Claude Code v2.1.257 or later. If you set both variables, subagents run on the model in `CLAUDE_CODE_SUBAGENT_MODEL`. If you set only `CLAUDE_CODE_SUBAGENT_MODEL_FORCE`, subagents run on the main conversation's model, except that the built-in Explore subagent runs on the model listed for it ... - Effort, verbatim: "When you ask Claude to run a non-fork subagent at a specific effort level, it can also pass an `effort` parameter for that invocation. The parameter overrides the `effort` field and stays in effect when the subagent is resumed. The `CLAUDE_CODE_EFFORT_LEVEL` environment variable takes precedence over both. The per-invocation parameter requires Claude Code v2.1.292 or later." — [sub-agents](https://code.claude.com/docs/en/sub-agents); CHANGELOG 2.1.292: "Added an `effort` parameter to the Agent tool, so Claude runs a sub-agent at the effort level you ask for" — [CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)
- Resume: "A per-invocation `model` parameter also applies when the subagent is resumed or sent a follow-up message, so the subagent stays on that model." — [sub-agents](https://code.claude.com/docs/en/sub-agents); CHANGELOG 2.1.211 "Fixed subagents spawned with an explicit model override reverting to the parent's model when resumed" — [CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)

- Forks: table row "Model | Same as main session | From the subagent's `model` field"; "Forks ignore `CLAUDE_CODE_SUBAGENT_MODEL_FORCE` for model selection, so they stay on the main conversation's model"; "A fork can't spawn further forks." — [sub-agents](https://code.claude.com/docs/en/sub-agents)
- Local, this session's Agent tool schema (2.1.314): `model` is an enum `["sonnet","opus","haiku","fable"]` described as "Optional model override for this agent. - CHANGELOG, older context: 2.0.28 "Subagents: claude can dynamically choose the model used by its subagents"; 2.1.72 "Restored the `model` parameter on the Agent tool for per-invocation model overrides"; 2.1.316 "Fixed sub-agents that inherited a parent sub-agent's model moving to the main model when a background job or message woke them"; 2.1.300 "Fixed agent hooks ignoring their `model`: aliases like `haiku` now resolve, a subagent's model no longer overrides it"; 2.1.296 "Added `CLAUDE_CODE_WORKFLOW_SUBAGENT_MODEL` to run every workflow agent on one model while other subagents keep theirs" — [CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)

### Inferences
- The Agent tool schema's own `effort` description instructs the orchestrator to set effort "ONLY when the user, or instructions such as CLAUDE.md or a skill, explicitly ask" — so a plugin that wants a role to run at, say, `low`, must say so explicitly in the skill text that drives the orchestrator, or put `effort:` in the agent definition (which needs no per-call opt-in). The definition route is the more reliable of the two.
- Because the per-call `model` is alias-only, a plugin cannot pin a *version* at call time; version pinning for a role must go in the agent's `model:` frontmatter (full ID) or in the user's `ANTHROPIC_DEFAULT_*_MODEL`.
- The family-alias quirk means `model: opus` in a definition does **not** guarantee the `opus` alias's version: if the user's main model is already an Opus (the account default is Opus 5.5), the subagent runs on the main model exactly, `[1m]` included. For a plugin that wants "cheaper than the orchestrator", `haiku`/`sonnet` aliases or full IDs are the robust choices.

### Gaps
- The docs do not say what happens when the per-call `model` names an alias the provider cannot resolve (e.g. `fable` on Foundry); only the `availableModels` substitution path is documented.

## Q4. Effort: settings `effortLevel` / `modelSettings` / `maxEffortLevel`, `CLAUDE_CODE_EFFORT_LEVEL`, `/effort`, `--effort`, per-model support, and the new `CLAUDE_CODE_SUBAGENT_EFFORT`

## Q5. Skills and custom slash commands: `model:` / `effort:` / `context: fork` / `agent:` frontmatter, and how forked skills pick their model

### Takeaway
In the main conversation a skill's `model:` applies "for the rest of the current turn", is not saved, and is a model switch (full cache re-read) for that turn; `effort:` likewise applies for the turn and loses only to `CLAUDE_CODE_EFFORT_LEVEL`. With `context: fork` both values "set the forked subagent's model/effort instead", the subagent is of the type named by `agent:` (default `general-purpose`), and it starts fresh (no conversation history, despite the name). Legacy `.claude/commands/*.md` accept the same frontmatter except `name` and `paths`.

### Cited Findings
- `model` row, verbatim: "Model to use when this skill is active. The override applies for the rest of the current turn and isn't saved to settings. The session model resumes when you send your next prompt. Accepts the same values as `/model`, or `inherit` to keep the active model. A value excluded by your organization's `availableModels` allowlist isn't used, and the session keeps its current model. In auto mode, and in plan mode while the classifier reviews commands, a model that auto mode doesn't support also isn't used ... With `context: fork`, the value sets the forked subagent's model instead, and an excluded value follows the same rules as a subagent model override." — [skills](https://code.claude.com/docs/en/skills)
- `effort` row, verbatim: "Effort level for the rest of the current turn. Overrides the session effort level, but not the `CLAUDE_CODE_EFFORT_LEVEL` environment variable. With `context: fork`, the value sets the forked subagent's effort level instead. When you omit it, the level comes from the effort resolution order. Options: `low`, `medium`, `high`, `xhigh`, `max`; available levels depend on the model." — [skills](https://code.claude.com/docs/en/skills)
- `context` ("Set to `fork` to run in a forked subagent context"), `agent` ("Which subagent type to use when `context: fork` is set"), `background` ("Only applies with `context: fork`. Set to `false` to wait ... Default: `true`") — [skills](https://code.claude.com/docs/en/skills)
- "Run skills in a subagent", verbatim: "Claude Code starts a new subagent of the type set in the `agent` field and gives it the skill content as its prompt. "The `agent` field determines the execution environment (model, tools, and permissions)." - Legacy commands: "a Markdown file in `.claude/commands/` is the older format and still works. - CHANGELOG 2.1.223: "Added a warning when workflow agents, forked skills, slash commands, or resumed background agents' requested subagent model is restricted and the parent model runs instead" — [CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)
- Local: no `SKILL.md` under `~/.claude/skills` or the installed plugin caches on this machine sets `model:`, `effort:`, `context:` or `agent:` (grep returned nothing), so there is no local precedent to inspect.

### Inferences
- For the plugin's entry skill (`SKILL.md` running in the main session), setting `model:` would switch the orchestrator's model for that turn and force a full cache re-read every invocation; `effort:` on that skill is the cheaper lever because on Opus 5.5 / Sonnet 5.5 / Haiku 5.5 / Fable 5.1 (API key or subscription) an effort change keeps the cache (Q7). - When `context: fork` names a custom `agent:` that itself has `model:`, the skill's `model:` "sets the forked subagent's model instead" reads as the skill winning (analogous to a per-invocation override), but the page never states the tie-break. Flagged as unverified.

### Gaps
- Precedence between a forked skill's `model:`/`effort:` and the named `agent:`'s own frontmatter `model:`/`effort:` is not documented.
- Whether the plugin-manifest `commands[].model` field accepts aliases, full IDs, or `inherit` is not stated beyond "string".

## Q6. Model aliases versus IDs on Bedrock / Vertex / Foundry, and the `ANTHROPIC_DEFAULT_*_MODEL` mapping

### Takeaway

## Q7. Prompt-caching implications of model and effort choices (subagent isolation; mid-session switches)

### Takeaway
A non-fork subagent has its own prefix and its own cache, and "The parent's cache is unaffected", so a different subagent model never invalidates the orchestrator's cache; a fork shares the parent's cache. Switching the main session's model is a full uncached re-read ("Each model has its own cache"); changing effort is too on most models but not on Opus 5.5 / Sonnet 5.5 / Haiku 5.5 / Fable 5.1 with an API key or subscription. Subagent requests get a 5-minute TTL by default even on a subscription.

### Cited Findings
- Verbatim: "A subagent starts its own conversation with its own system prompt and tool set, separate from the parent's. Its first request doesn't read the parent's cache, because the two prefixes differ, and it warms a cache of its own across its turns. Subagents fall outside the main-conversation TTL bucket, so they get five minutes even on a subscription until you choose a longer one. The parent's cache is unaffected. From the parent's side, the subagent's call and result append to the conversation, leaving the parent's prefix intact. A fork, by contrast, inherits the parent's system prompt, tools, and conversation history exactly, so its first request reads the parent's cache." — [prompt-caching](https://code.claude.com/docs/en/prompt-caching)
- Fork table: "Prompt cache | Shared with main session | Separate cache"; "a fork costs less than a fresh subagent for tasks that need the same context" — [sub-agents](https://code.claude.com/docs/en/sub-agents)
- Model switch: "Each model has its own cache. Switching with `/model` means the next request reads the entire conversation history with no cache hits, even though the content is identical." Claude Code asks for confirmation only while the cache is warm (v2.1.238+); `opusplan` "each plan-mode toggle is a model switch and starts a fresh cache"; automatic safety fallback is also a model switch — [prompt-caching](https://code.claude.com/docs/en/prompt-caching)
- Effort change: "On most models, changing the effort level mid-session means the next request reads the entire conversation history with no cache hits ... On Opus 5.5, Sonnet 5.5, Haiku 5.5, and Fable 5.1 with an API key or a Claude subscription, you keep the cache when you change effort ... On Amazon Bedrock, Google Cloud's Agent Platform, or a Claude apps gateway, or when you set `CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS` or your organization has a HIPAA configuration, it works as on most models. Before v2.1.260, changing effort on Fable 5.1 ... also invalidated the cache." — [prompt-caching](https://code.claude.com/docs/en/prompt-caching)
- Cache scope: "two requests share a cache only when their model, speed, and prefix match" — [prompt-caching](https://code.claude.com/docs/en/prompt-caching)
- TTL buckets: "Main conversation | One hour (Claude subscription, within plan usage) | Five minutes (usage credits, API key, cloud provider)"; "Everything else [subagents, workflows, teammates, forks, compaction, titles] | Five minutes, except the server-controlled helper requests". Controls: `promptCacheTtl` / `CLAUDE_CODE_PROMPT_CACHE_TTL` (main), `subagentPromptCacheTtl` / `CLAUDE_CODE_SUBAGENT_PROMPT_CACHE_TTL` (everything else), both `5m`|`1h`, v2.1.242+; per-subagent `experimental.cacheTtl` frontmatter (v2.1.248+; "Claude Code ignores a `1h` there while your Claude subscription is using usage credits"); order: `FORCE_PROMPT_CACHING_5M=1` > bucket env var > bucket setting > `experimental.cacheTtl` > `ENABLE_PROMPT_CACHING_1H=1` > bucket default — [prompt-caching](https://code.claude.com/docs/en/prompt-caching), [env-vars](https://code.claude.com/docs/en/env-vars)
- Resumed subagents: "the resumed run's first request can read the cache the original run warmed" — [prompt-caching](https://code.claude.com/docs/en/prompt-caching)
- Plugin enable/disable: "Claude Code never invalidates the cache for a plugin's skills, commands, agents, hooks, monitors, or themes" (appended after the conversation); MCP-server plugins follow the MCP rules — [prompt-caching](https://code.claude.com/docs/en/prompt-caching)
- Per-model caching kill switches: `DISABLE_PROMPT_CACHING_{HAIKU,SONNET,OPUS,FABLE}` apply to the model the alias resolves to; `DISABLE_PROMPT_CACHING` to all — [model-config](https://code.claude.com/docs/en/model-config)
- `/usage`'s `Prompt cache (main)` line "covers the main conversation only, not subagents" (v2.1.251+) — [costs](https://code.claude.com/docs/en/costs)
- Tip: "Pick your model and effort level at the top of a session, then save `/compact` for natural breaks between tasks." — [prompt-caching](https://code.claude.com/docs/en/prompt-caching)

### Inferences
- For the plugin's design, routing review/verification/planning/scoping to subagents on cheaper models is cache-neutral for the orchestrator. The one cache-hostile pattern is a skill `model:` on the orchestrator's own turn (Q5).
- Same-role subagents spawned repeatedly with identical system prompts (same agent definition, same tool set, same CLAUDE.md) can hit each other's cache within the 5-minute TTL, since the cache is keyed on model+speed+prefix; the docs state this sharing only for workflow fan-outs and resumed subagents, so treat cross-spawn reuse as plausible rather than promised.

### Gaps
- No doc quantifies a subagent's first-request cost relative to the parent's context (it depends on CLAUDE.md size and the agent's system prompt); the only lever named is `omitClaudeMd`.

## Q8. Subscription (Pro/Max/Ultra) versus API key: does a cheaper subagent model reduce usage-limit consumption, and what do the built-in Explore/Plan agents run on

### Takeaway
Official pages say subagent requests "count toward the same usage limits as your main conversation", that Max has a five-hour limit, a weekly limit "across all models", and a separate weekly Fable limit, and that model-specific limit messages ("You've hit your Opus limit") exist; none states a per-model consumption rate, so "haiku subagents cost less of my Max limit" is not documented. Explore inherits the main model (and on a subscription moves to the `opus` alias when the main model is Fable); Plan inherits unless forced.

### Cited Findings
- "Subagents send their own requests, which count toward the same usage limits as your main conversation." — [sub-agents](https://code.claude.com/docs/en/sub-agents)
- "The subagent's own requests still draw on your usage. To spend less on them, choose a smaller model for a subagent or run every subagent on one model." and "For simple subagent tasks, specify `model: haiku` in your subagent configuration." — [costs](https://code.claude.com/docs/en/costs)
- Limit messages: "'You've hit your session limit' or 'You've hit your weekly limit': a seat-based usage window on a subscription plan, shared across all models, so the developer can't restore access by switching models with `/model`. ... After the model-specific 'You've hit your Opus limit' or 'You've hit your Sonnet limit' message, switching to a model outside that family with `/model` does keep the developer working." — [costs](https://code.claude.com/docs/en/costs)
- `/usage` on a subscription shows "Attribution: recent usage attributed to skills, subagents, plugins, and individual MCP servers, each shown as a percentage of the total" and recommendations such as "Switch from max to high effort · /effort high"; the Session block's dollar figure "isn't relevant for billing" for subscribers — [costs](https://code.claude.com/docs/en/costs)
- Max plan: "a five-hour limit", "a weekly usage limit that applies across all models", "a separate weekly limit for Fable"; "Anthropic may limit your usage in other ways, such as weekly and monthly caps or model and feature usage, at our discretion." The page does not say any model consumes limits faster — [What is the Max plan?](https://support.claude.com/en/articles/11049741-what-is-the-max-plan)
- Pro/Max/Ultra with Claude Code: "Pro and Max plans have a five-hour session limit and a weekly limit"; "These limits are shared across Claude and Claude Code"; "Max and Ultra plans also have a separate weekly limit for Fable"; "Monthly API credits included with the Max plan can't be used in Claude Code"; usage credits are "billed at standard API rates". When the main conversation runs Fable, Explore's model depends on how you connect: With a Claude subscription, an Anthropic Console account, or an LLM gateway reached through `ANTHROPIC_BASE_URL`, Explore runs on the Opus model that the `opus` alias resolves to. On Amazon Bedrock, Google Cloud's Agent Platform, Microsoft Foundry, Claude Platform on AWS, or a Claude apps gateway, Explore stays on the main conversation's model." Plan: "inherits from the main conversation, unless you set `CLAUDE_CODE_SUBAGENT_MODEL` and force it onto every subagent". General-purpose: "the `CLAUDE_CODE_SUBAGENT_MODEL` model if you set one and nothing assigns a model another way, otherwise the main conversation's model". `claude`: "None of its own; follows the model order". `statusline-setup`: Sonnet. `claude-code-guide`: Haiku — [sub-agents](https://code.claude.com/docs/en/sub-agents)
- "Setting `CLAUDE_CODE_SUBAGENT_MODEL` by itself doesn't change the model the built-in Explore and Plan subagents run on." A user/project subagent named `Explore` overrides the built-in and keeps its own `model` field ("`model: haiku` runs exploration on a lower-cost model"). `CLAUDE_CODE_DISABLE_EXPLORE_PLAN_AGENTS=1` removes Explore and Plan (v2.1.198+); `permissions.deny` `"Agent(Explore)"` blocks one type — [sub-agents](https://code.claude.com/docs/en/sub-agents), [env-vars](https://code.claude.com/docs/en/env-vars)

## Q9. Documented per-model and per-feature restrictions relevant to role-based selection

### Takeaway
The main restrictions are: effort availability varies by model (no effort at all on Sonnet 4.5 / Haiku 4.5 / Opus 4.1 and earlier; no `xhigh` on Opus 4.6 / Sonnet 4.6); `max` effort is session-only; thinking cannot be disabled on the 5.5 models or Fable; Fable 5.1 needs v2.1.257+, is never the default, may bill to usage credits, and apps-gateway sessions resolve `fable` to Fable 5; `haiku` is rejected as a value of `ANTHROPIC_DEFAULT_MODEL`; `[1m]` on the 4.6 models is plan-gated; `deniedModels`/`availableModelsMatch` are managed-only.

### Cited Findings
- Effort support table and fallback rule — [model-config](https://code.claude.com/docs/en/model-config); `CLAUDE_CODE_ALWAYS_ENABLE_EFFORT` excludes "Claude Opus 4.1, Claude Sonnet 4.5, Claude Haiku 4.5, and earlier models" because they reject the parameter — [env-vars](https://code.claude.com/docs/en/env-vars)
- "`max` applies to the current session only unless set through `CLAUDE_CODE_EFFORT_LEVEL`"; `effortLevel` setting accepts only `low`..`xhigh` — [model-config](https://code.claude.com/docs/en/model-config), [settings-reference](https://code.claude.com/docs/en/settings-reference)
- "You can't turn off thinking on Opus 5.5, Sonnet 5.5, Haiku 5.5, or the Fable models, which always use extended thinking." — [costs](https://code.claude.com/docs/en/costs); `alwaysThinkingEnabled: false` "has no effect" on models that always think — [settings-reference](https://code.claude.com/docs/en/settings-reference)
- Fable: v2.1.257+; never the default; usage-credit billing on some plans; apps-gateway `fable`/`best`→Fable 5 — [model-config](https://code.claude.com/docs/en/model-config)
- `ANTHROPIC_DEFAULT_MODEL` "is ignored when set to `default`, `inherit`, `opusplan`, or `haiku`" — [model-config](https://code.claude.com/docs/en/model-config)
- Skill `model:` not applied "In auto mode, and in plan mode while the classifier reviews commands, a model that auto mode doesn't support" — [skills](https://code.claude.com/docs/en/skills); CHANGELOG 2.1.302 "Added `CLAUDE_CODE_AUTO_MODE_MODEL` to choose the model the client-side auto mode classifier uses" (CHANGELOG-only here; not checked on the permission-modes page) — [CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)
- Context window differences: Opus 4.6 / Sonnet 4.6 compact at 200K unless `[1m]`; native-1M models compact at about 967K; `CLAUDE_CODE_DISABLE_1M_CONTEXT=1` holds native-1M models at 200K; unrecognized IDs are assumed 200K (`CLAUDE_CODE_MAX_CONTEXT_TOKENS` corrects it) — [model-config](https://code.claude.com/docs/en/model-config)
- `deniedModels` and `availableModelsMatch`: "Scope: Managed. Claude Code ignores the key in user, project, and local settings and in `--settings`, with a warning." — [settings-reference](https://code.claude.com/docs/en/settings-reference)
- Fast mode: separate cache; "If your current model doesn't support fast mode, enabling fast mode also switches you to Opus" — [prompt-caching](https://code.claude.com/docs/en/prompt-caching); CHANGELOG 2.1.316 "Deprecated fast mode for Opus 4.8 as of October 30, 2026; it will be removed on November 30, 2026" — [CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)
- Bedrock/Vertex: Haiku "may not be enabled in every account or region"; Foundry "has no equivalent startup check" and shows errors for unavailable defaults — [amazon-bedrock](https://code.claude.com/docs/en/amazon-bedrock), [model-config](https://code.claude.com/docs/en/model-config)

### Inferences
- A plugin role pinned to `effort: max` is well-defined only on Fable and the 5.x / 4.7 / 4.8 models; on Opus 4.6 / Sonnet 4.6 it runs as `max` (supported there) but `xhigh` would silently become `high`. Roles should name effort as an intent and accept the documented step-down.

### Gaps

## Q10. The settings precedence chain as it applies to `model`, effort keys, and `env`

### Takeaway
Managed > `--settings` (command line) > project local > shared project > user; environment variables are not a level but are decided per pair (`ANTHROPIC_MODEL` beats any file's `model`; `--model` beats both; `CLAUDE_CODE_EFFORT_LEVEL` beats `--effort` and `/effort`); an `env` block is an ordinary key that follows the levels, overwrites shell exports, and (for model-selection variables) applies at startup from every file including project files; `maxEffortLevel` and the host-managed-provider case are the documented exceptions.

### Cited Findings
- Verbatim stack: "1. Managed settings ... Nothing in your own settings files or `--settings` overrides a managed key, and a flag such as `--model` picks only from the models your organization allows. A managed `model` is a starting default, not a lock; the locks are `availableModels` and `deniedModels`. 2. Command line: JSON you pass with `--settings` ... Other flags, such as `--model`, set one thing for the session and aren't part of this stack 3. Project local settings (`.claude/settings.local.json`) 4. Shared project settings (`.claude/settings.json`) 5. User settings (`~/.claude/settings.json`)" — [settings](https://code.claude.com/docs/en/settings)
- "Environment variables aren't a level in this stack. When a behavior has both a shell variable and a settings key, which one applies is decided per pair, not by level: `ANTHROPIC_MODEL` exported in your shell applies over the `model` key from any file, while `ANTHROPIC_DEFAULT_MODEL` applies only when no file sets `model`. ... An `env` block inside a settings file is an ordinary key and follows the levels above." — [settings](https://code.claude.com/docs/en/settings)
- "`ANTHROPIC_MODEL` overrides the `model` setting, and `--model` overrides both for a session." — [settings](https://code.claude.com/docs/en/settings); "`--model` and `/model` override `ANTHROPIC_MODEL`, while `CLAUDE_CODE_EFFORT_LEVEL` overrides `--effort` and `/effort`." — [env-vars](https://code.claude.com/docs/en/env-vars)
- Flags for keys: "`--model` for `model` and `--effort` for `effortLevel` and `modelSettings`"; `--settings` "applies it above your user, project, and local files and below managed settings" — [settings](https://code.claude.com/docs/en/settings)
- `env` entry: Scope `Any file`; "A value here overwrites the same variable exported in your shell, and when more than one settings file sets a variable, the highest-precedence one applies"; Desktop app / self-hosted runner launch environments take precedence over file `env`; set a variable to `""` to cancel a shell export; "Variables Claude Code classifies as safe, such as model selection, timeouts and limits, and feature toggles: at startup from every settings file, apart from the variables project and local settings can't set" — [settings-reference](https://code.claude.com/docs/en/settings-reference)
- Variables project/local cannot set: config-dir/temp-dir variables, Windows program variables, session-content exporters, OpenTelemetry on/endpoint/content variables (v2.1.282+), startup/sync variables, `CLAUDE_AX_*`, dialog-timeout and attachment toggles, host-owned identity variables. The `ANTHROPIC_*MODEL*`, `CLAUDE_CODE_SUBAGENT_MODEL*`, and `CLAUDE_CODE_EFFORT_LEVEL` variables are not on that list — [settings-reference](https://code.claude.com/docs/en/settings-reference)
- "Between settings files, `env` values follow settings precedence, so a managed settings entry overrides the same variable in user or project settings." — [env-vars](https://code.claude.com/docs/en/env-vars)
- Lists merge except `fallbackModel` (whole chain from highest file), `modelPicker` (user/managed/`--settings` only), `availableModels` (managed list applied as-is), `modelSettings` (resolved per model with `effortLevel`) — [settings](https://code.claude.com/docs/en/settings)
- Exceptions to managed precedence relevant here: `maxEffortLevel` "A lower cap from any scope, including `--settings`" wins (v2.1.267+); `CLAUDE_CODE_PROVIDER_MANAGED_BY_HOST` makes the embedding app's model config beat managed `model`, `fallbackModel`, `modelPicker`, `modelOverrides` and managed `env` `ANTHROPIC_MODEL` / `ANTHROPIC_DEFAULT_*_MODEL`, while a managed `availableModels` stays in force — [settings](https://code.claude.com/docs/en/settings), [env-vars](https://code.claude.com/docs/en/env-vars)
- Project `env` waits for trust in interactive sessions: "From project and local settings: after you trust the workspace, or at startup in `-p` mode" — [settings-reference](https://code.claude.com/docs/en/settings-reference); "most `env` values apply only after each teammate trusts the folder" — [settings](https://code.claude.com/docs/en/settings)
- Cloud sessions read only some files (shared project `.claude/settings.json` in single-repo sessions; never user or local; server-managed settings apply) — [settings](https://code.claude.com/docs/en/settings)
- `model` and `effortLevel`/`modelSettings` are "read only once, at session start"; use `/model` and `/effort` mid-session — [settings](https://code.claude.com/docs/en/settings)
- Plugin `settings.json`: only `agent` and `subagentStatusLine` take effect; "plugin defaults are the lowest layer" — [plugins/components](https://code.claude.com/docs/en/plugins/components), [plugins/manifest-reference](https://code.claude.com/docs/en/plugins/manifest-reference)

### Inferences
- A consuming project can legitimately commit `.claude/settings.json` with an `env` block such as `{"CLAUDE_CODE_SUBAGENT_MODEL": "haiku"}` and it applies (after trust) from the shared project file, below the user's and managed `env`. That is the only committed, project-scoped surface for subagent model defaults that does not require editing agent definitions; it is a *default*, overridden by any agent's `model:` or per-call model unless the same block also sets `CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1`.
- A plugin cannot ship an `env` block (plugin `settings.json` drops every key except `agent` and `subagentStatusLine`), so plugin-side control is limited to agent frontmatter, skill frontmatter, and the instructions it gives the orchestrator for per-call `model`/`effort` parameters.

### Gaps
- The docs do not state where a `--agents` CLI definition's `model` sits relative to `ANTHROPIC_MODEL` or the `model` key when that agent is also the main-session `--agent`.
