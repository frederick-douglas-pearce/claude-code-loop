# Loop metrics baseline — 0.3.0, 2026-10-04

**Purpose:** freeze the **0.3.0** numbers that the engine-sharding release (#133, S5) is judged
against, with its predictions stated in advance (#126). D008 pins the before-baseline to the release
installed immediately before the sharding cut, which is 0.3.0. **This is not `baseline-2026-08-25.md`
updated.** That doc stays frozen at 0.2.0 and gains pointer notes only. The engines differ by +50.8%
and their sessions ran in different strata, so nothing here is comparable to it.

**Frozen at:** `main` @ `3725ee5`, plugin **0.3.0** installed in every measured repo (confirmed from
`~/.claude/plugins/installed_plugins.json`, 2026-10-04).
**Stratum:** parent `claude-opus-5-5`@`high`, sessions started on or after 2026-09-27T00:00Z and before
the harvest start, 2026-10-04T21:16Z.
**Measured with:** `docs/research/engine_cost.py` as fixed in #126 (see *Instrument fix*), run with
no `--floor`, so each session's floor is derived from its engine era.

## Units, and what P2 is

- **P2 (ingested)** and P3 are in **context tokens**: the context-window deltas `engine_cost.py`
  attributes to engine reads. Not `chars/4`, and not the file size. P5 is in context tokens too (the
  peak).
- **P2 means all engine text the parent loads: core plus units.** On 0.3.0 that is `loop-engine.md`
  alone. `engine_cost.py` counts only `loop-engine.md` reads, so #133 must extend it to count
  `phases/` and `reference/` reads (#133/AC4).
- **P2c** is `resident_turns / processed`. It is dimensionless, and it is #133's primary acceptance
  metric.
- **No P2-to-always-loaded ratio is printed here** (#126/AC5). The unit of that ratio is #223's open question.

## Instrument fix (#126)

**The defect.** `classify()` treated any path containing `/plugins/` as a plugin-cache load. Since
#170 the working tree itself sits under `plugins/dev-loop/`, so in-repo engine reads in
`claude-code-loop` sessions were scored as loads. The discriminator is now `/.claude/plugins/cache/`.

Two qualifying sessions were affected:

| session | P2, old tool | P2, fixed tool |
|---|---:|---:|
| `de7e4367` | 127,654 | 101,828 |
| `b5129651` | 112,120 | 101,944 |

vote and esg are unaffected.

**One other reclassification, and why.** Claude Code keeps a git clone of each marketplace at
`~/.claude/plugins/marketplaces/<name>/`, the source it installs from. It runs only the copy under
`~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/`, which is `${CLAUDE_PLUGIN_ROOT}`. An agent
reading the marketplace clone is reading a file, not loading the engine that executes, so it is no
longer counted.
- No qualifying session reads the clone, so no figure on this page moves.
- One session that did read it: esg `ec516428` (4 greps on 2026-09-07), which is pre-0.3.0 and
  inadmissible either way.

**What covers it.** `test_payload_working_tree_read_is_tree_not_load` and
`test_non_cache_copies_under_dot_claude_are_not_loads` in `test_engine_cost.py`. **CI does not run
them**: it discovers only `tests/`. Run them by hand with `python3 docs/research/test_engine_cost.py`.

- inside the window above;
- admissible;
- not being written at harvest.

Every qualifying session's subagents also ran `claude-opus-5-5`@`high`, or the session spawned none.
That makes the 2026-09-27 boundary safe on the agents' side too. **The qualifying set is frozen as
the session IDs listed below.** A re-run admits nothing outside this list, and an exclusion made
because a file was live at harvest stays excluded.

**Session class**, read from what the session itself wrote to its journal, never from which engine
files it read:
- **completed iteration:** wrote a `- Budget:` line;

31.2%. `7be48522` journalled a re-entry at step 5, then ran the plan gate and every later step in that

## Predictions for the sharding release, stated in advance

**After side:** the sharding release (v0.3.1) as installed in the treated repos per #133/AC2, parent
`claude-opus-5-5`@`high`. No other stratum is comparable.

Sizes are the in-tree ones at `3725ee5`: core 200,789 B; `reviewing` 32,344 B, loaded at step 8;
`accepting` 38,409 B, loaded at step 10. **If the release commit's sizes differ, re-derive from the
formulas below.**

| # | metric | 0.3.0 baseline (loop · vote · esg) | predicted (loop · vote · esg) |
|---|---|---|---|
| P1 | always-loaded | 277,829 B | **211,618 B (−23.8%)** |
| P2 | context tokens, completed iteration | 101,967 · 102,091 · 101,985 | **≈103,500 each (+1.5%)** |
| P3 | context tokens, plan-gate stop | not measured | **≈76,500 (−25% vs one complete 0.3.0 load, ≈102,000)** |
| P2c | completed iterations | 31.0% · 29.0% · 33.1% | **27.4% · 25.5% · 29.4%** |
| P9, P5–P7 | — | above | **unchanged**; a drop in P6/P7 is a red flag (#133/AC3) |

**How each is derived:**
- **P2 and P3:** ingestion scales with the bytes loaded, at the measured 0.3.0 rate of ≈0.381 context
  tokens per engine byte. A completed iteration loads core plus both units, 1.0146 × 0.3.0's `loop-engine.md`
  bytes; a plan-gate stop loads core only, 0.7502 ×. Sharding defers text rather than deleting it, so P2 for
  a completed iteration is not predicted to fall.
- **P2c:** P2c′ = s·k / (1 − s + s·k), where s is the baseline and k is the factor by which engine
  resident-turns scale. With k = 0.8405: k = (core + 0.45 × reviewing + 0.25 × accepting) ÷ 0.3.0
  engine bytes.

**Assumptions, stated rather than measured:**
1. **Each unit is read once per iteration.** Each extra `reviewing` read adds ≈12,300 context tokens;
   two reads give P2 ≈115,800.
2. **`reviewing` arrives 55% of the way through a session's turns and `accepting` 75%.** These are
   assumed. Reviewing at 40–60% and accepting at 70–90% gives k = 0.813–0.866, and P2c of
   26.8–28.0% · 24.9–26.1% · 28.7–30.0%. #133 measures the real arrival centroids.
3. **Non-engine context is unchanged.** Working-tree engine reads (`tree`) sit in
   processed context, so a change in how much engine-editing work the after side does moves loop
   P2c on its own.
4. **The class mix is the same** on both sides. See the class split above.

**These are model point predictions of a per-repo median, and at this n the sampling spread is
comparable to the effect.** For example, the loop completed-iteration median of 31.0% (n=8) has a
distribution-free ~93% interval of 27.2–36.4% (order statistics 2 and 7), which contains the
predicted 27.4%. How #133 separates an effect from a null is #133's and #128's design, not this
page's.
