# Per-role, multi-provider model selection for the dev loop — design

**Status:** design, not a ruling. Nothing here has been through a gate.
**Date:** 2026-10-31. **Engine:** 0.4.0 installed; working tree `main` at `3287e97`. **Claude Code:** 2.1.314 running the research session, 2.1.316 installed; every `code.claude.com` page cited was fetched 2026-10-31. **Question:** how should a consumer of the dev-loop plugin choose a model and effort level per role, including models from providers other than Anthropic, without the engine learning anything about a provider?

Five research notes feed this document, all in `docs/research/model-selection-2026-10-31/`; `notes/<file>` below means a file in that directory, and a section mark after it (`§A`, `Q3`, `KQ2`) names the section of the note that carries the claim. Each note carries its own dated citations to primary sources, and where a note labels a claim inferred, unverified, or a gap, this document carries the same label. The design decisions were taken by the coordinating session after all five notes were in (`notes/PROGRESS.md` → "Decisions taken"); this document argues them rather than re-opening them. Nothing was re-fetched for this document.

---

## 1. The one-paragraph answer

Put the tiers in the config, make the four Claude Code model aliases the contract, and leave the provider at the edge. One new `CAPS` parameter, `MODEL_TIERS`, binds each role the engine spawns to a tier and an optional effort (`finder: inherit`, `mutation: sonnet@medium`), where a tier is one of `inherit|haiku|sonnet|opus|fable` — the four named tiers being the only values the Agent tool's per-call `model` parameter accepts, and `inherit` meaning the parameter is not passed (`notes/claude-code-native-surfaces.md` Q3). The engine passes the bound values on each spawn and journals what it passed in a `models=` slot on the `- Budget:` line; a role the table does not name, or names with anything the engine cannot read as a tier, resolves to `inherit`, and the engine then passes neither parameter — today's behavior, which is the whole of what the fallback promises, and the journal marks an entry it could not read so a typo is seen. The consumer's environment decides what a tier *is*: `ANTHROPIC_DEFAULT_{FABLE,OPUS,SONNET,HAIKU}_MODEL` pin each alias to a model ID, which is the recipe the third-party provider guides converge on — `OPUS`, `SONNET`, `HAIKU`, increasingly `FABLE` (`notes/third-party-providers-and-gateways.md` Q1) — so the same config is accepted unchanged by Anthropic, Bedrock, DeepSeek, or a LiteLLM gateway without the engine naming any of them; accepted as syntax, since no provider profile has been run, which is §7.8's phase 3. The headline numbers are modeled, not measured: subagents are 33–38% of the whole-tree bill and every one of them runs `claude-opus-5-5` today (F198; `notes/dev-loop-internals.md` §B); the cost review's R4 prices tiering at 7–15% whole-tree with the judgment roles kept on the main model; Anthropic's one controlled measurement of Haiku subagents under an Opus orchestrator is −32% cost per attempt at −4 points pass rate, which bounds what cheapening subagents can do (`notes/prior-art-and-evidence.md` KQ3). The limit on v1 is structural: the implementer runs in the parent thread (`loop-engine.md` step 6; D017), so the role that writes code, tests, and docs is not addressable from the table until a non-fork writing spawn exists — R1's fix agent is the first, and R2's forked phases do not qualify, since a fork ignores both parameters — and in v1 the only lever on it is the session's own model and effort. That is why v1 also supports the inverted roster (§6, option 13): a cheaper or lower-effort session with the judgment roles tiered *up*, which reaches the parent's share of the bill with no new mechanism and is the honest v1 answer to "a cheap model for docs writing" — run a docs-heavy slice of the backlog on the cheaper tier with the reviewers tiered up.

## 2. What was asked, and what the goals weigh

Fred asked for per-task model selection in the loop — a cheap model for implementing and reviewing docs, Sonnet for test development and review — with the harder requirement that models from other providers be usable, and three goals in his order of emphasis: save significant cost, possibly cut runtime, and, most important, make the loop more marketable to new users. Open questions: configured in `loop.config.md`, a new config, or something else; implemented through Mods, hooks, or something better; and easy to configure within the loop (`notes/PROGRESS.md` → "The request").

The research changes what each goal is really served by.

**Cost.** The bill is turn-driven (`cost ≈ turns × ~25k` billable-equivalent on 0.3.1), and every lever shipped so far acted on context and moved nothing measurable (`cost-review-2026-10-26.md` §1). Model tiering acts on the subagent third of the bill, which is why R4 ranks fourth, after fix application, phase isolation, and engine deletion. Two further findings narrow the cost case. First, Haiku 5.5's list price — $0.10 input / $0.50 output per million tokens, surfaced by a search summary and not re-fetched (`notes/claude-code-native-surfaces.md` Q8) — already sits in the cheap-third-party band: DeepSeek Flash $0.30/$1.20, GLM-5.3-Flash $0.15/$0.50, MiniMax-M3.1-Flash $0.15/$0.60, gpt-6-luna $0.10/$0.50, qwen-flash $0.05/$0.40 (`notes/third-party-providers-and-gateways.md` Q7). Cross-provider routing therefore buys little at the cheap tier that a Haiku tier does not, and it costs prompt caching on several paths (DeepSeek ignores `cache_control`; Ollama lists caching as unsupported; LiteLLM injects it only on `anthropic/` routes) in a workload where 97.6–98.9% of input is cache-read (`docs/research/README.md`, via `notes/dev-loop-internals.md` §B). Second, three of the four "cheaper model" roles R4 names do not exist as spawns: ledger probes, step 0/1 reconciliation, and CI wait are parent turns; docs propagation and green-up are notebook proposals (`notes/dev-loop-internals.md` §A, Inferences). The measurable surface of a first tiering PR is the mutation selector, ad-hoc exploration, and a contested half of the AC-verifier.

**Runtime.** No note measures a runtime effect. The one vendor figure is Haiku 4.5 at "more than twice the speed" of Sonnet 4 (`notes/prior-art-and-evidence.md` KQ5). Finders already run in parallel, so a faster finder shortens the review gate only by the slowest member, and in the one hand-checked session active API time was 4.5h of a 29h span — the other 24.6h was the human (R9). Runtime is a secondary effect of this design, and the document does not claim one.

**Marketability.** This is where the design earns its keep. Every surviving coding tool exposes a global default plus per-role overrides in the same value syntax, with secondary roles defaulting to inherit; named presets sit above that layer (`notes/prior-art-and-evidence.md` KQ2, KQ6). Users recognize that shape. The provider recipe — `ANTHROPIC_BASE_URL` plus alias pins — is what the guides for DeepSeek, Kimi, Z.ai, MiniMax, Alibaba, Ollama, OpenRouter, and Vercel converge on, pinning `OPUS`/`SONNET`/`HAIKU` and increasingly `FABLE`, though not uniformly: Z.ai's guide pins `OPUS` and `SONNET` only, Ollama's uses `--model`, and DeepSeek and MiniMax pin every alias to one model, Kimi all but `HAIKU` (`notes/third-party-providers-and-gateways.md` Q1). A config that binds roles to alias tiers is accepted unchanged by all of them — syntax, not a working run — and on a profile that pins every alias to one model the table changes nothing, because every tier is the same model. What a README can honestly say, once a profile has been run (§7.8, phase 3), is "bring your own models, per role, through the harness's own mechanism" — not "the loop runs well on GPT" — because no independent benchmark of the Claude Code harness driving non-Claude models exists (`notes/third-party-providers-and-gateways.md` Q8), and Anthropic's position is that it "doesn't support routing Claude Code to non-Claude models through any gateway" (Q2).

The constraints the design must honor come from the root `CLAUDE.md` and are summarized in `notes/dev-loop-internals.md` §D: the engine is project-agnostic and reads config by `CAPS` name only; a rule about safe states is written default-deny; wording that lands in the `/init-loop` skeleton is stranded in every consumer config, so its evidence bar is higher; anything that ships or that the suite runs is stdlib-only; a file ships iff a consumer needs it in the cache; and the loop runs the installed plugin, so no change takes effect before a release and a re-install.

Four facts from the table carry the design.

The subagent share is a third of the bill, measured on 0.3.1 at the `claude-opus-5-5@high` stratum: loop median $17.61 per session (n=5), vote $35.61 (n=11), subagent share 34–38% and 33% (`cost-review-2026-10-26.md` §2.1). Subagent *returns* are 0.9–3.7% of parent input, so constraining them is not a lever; what the subagents cost is their own context. One session's two built-in `Explore` agents were 21M of a 77M subagent context tree, on the main model (R9; appendix D).

The implementer is a parent turn by decision. D017 ruled `implementing` out of extraction because the staging and authoring rules are consumed at every commit boundary; cost review R2 leaves it in the parent for the first increment; R1 moves only *fix application* into a fresh agent in an isolated copy (`notes/dev-loop-internals.md` §A). The engine has no lever to re-model the implementer short of creating a writing spawn, which inherits the four isolation duties.

"Mechanically verified" is a property of a role's output, and the AC-verifier's Part 1 fails that test as written: its inputs are mechanical, but what it returns is a met/not-met judgment on every criterion that the orchestrator may not replace (`accepting.md`, via §A Inferences). R4's "mechanical Part 1 checks" reads as the input-retrieval half, and there is no separate spawn for that half today.

#281, the open issue for R4, contradicts the repo in two places a designer must resolve (`notes/dev-loop-internals.md` §E). It tiers "ledger probes and step 0/1 reconciliation" and "CI wait", which are parent turns, not spawns. And it says "Pin `model:` and `effort:` per role" in frontmatter, while the only frontmatter-bearing agents (`pm`, `architect`, `ba`) are user-global files that the engine forbids the orchestrator from editing (`loop-engine.md` hard limits) and that `/init-loop` cannot infer. The design below resolves both: parent turns are out of v1's scope by name, and the mechanism is the per-call parameter, which outranks frontmatter anyway.

Three caching facts bound the design (`notes/claude-code-native-surfaces.md` Q7). A non-fork subagent has its own prefix and its own cache; "The parent's cache is unaffected", so a different subagent model never invalidates the orchestrator's cache, while a fork shares the parent's. Subagent requests "get five minutes even on a subscription until you choose a longer one" (`subagentPromptCacheTtl`, `experimental.cacheTtl`). A main-session `/model` switch, an `opusplan` plan-mode toggle, or a skill `model:` on the orchestrator's own turn is a full uncached re-read; an effort change keeps the cache on Opus 5.5 / Sonnet 5.5 / Haiku 5.5 / Fable 5.1 with an API key or subscription, but not on Bedrock, Vertex, or an apps gateway.

Two quirks recur later. A family alias such as `opus` in the per-call parameter or frontmatter resolves to the main conversation's *exact* model when the main model is in that family, `[1m]` included, and on a non-Anthropic provider whenever Claude Code cannot tell the main model's family (`opus` only; not when `ANTHROPIC_DEFAULT_OPUS_MODEL` is set) (Q3). And the built-in `Explore` inherits the main model since v2.1.198 — on a subscription, Opus when the main model is Fable — and `CLAUDE_CODE_SUBAGENT_MODEL` alone does not move it; a custom agent named `Explore` with `model: haiku` does (Q8).

Two readings follow. Across tools the routable roles are *phase* roles, *agent* roles, and *bookkeeping* roles, and only the bookkeeping class is routinely defaulted to a cheaper tier by the vendor; phase and agent roles default to inherit (KQ2, Inferences). And `inherit` as the universal default is the fail-safe choice for a supervised loop in one exact sense: an unset binding changes nothing — the spawn gets no parameter and runs as it does today (KQ6, Inferences). That is safe as *today's behavior*, not as a quality floor: a session already on a cheaper model has nothing above it to fall back to, which §7.1 takes up. Goose is the caution: its lead/worker env-var feature, with turn-count switching between a planning model and an execution model, was removed within about a year of its 2025-08-11 announcement, along with the Planning Mode that replaced it; the current AutoPilot schema could not be verified (four URL variants returned 404 on 2026-10-31). Every surviving design is static per role or per mode (KQ2).

**Anthropic's measured guidance** (KQ3, all pages fetched 2026-10-31, undated). "Tuning effort is often a better lever than switching models"; sweep effort on one model first, then "price the stronger model alone at low effort", and build a pairing only if it beats the single model's whole curve. The effort sweep on Opus 5.5 over a SWE-bench Pro subset runs `low` 87.4% solved at $0.11/task to `xhigh` 96.7% at $0.74 — a wider range than the tier gap between Haiku 4.5 and Opus 4.5 on SWE-bench Pro public (39.45 vs 45.89) (KQ5). "Upgrade the model" is "up to 87% less per solved task on a coding benchmark". The one controlled subagent result: Haiku 5.5 subagents under Opus 5.5 at `medium` "cut cost per attempt by 32% and the pass rate by about 4 percentage points (95% interval 1.3 to 7.1)" — about what a mix of `low` and `medium` effort without subagents gives at that cost, "an alternative to lowering effort, not better". The advisor results are the warning about escalation designs: a strong model consulted at the weak model's discretion was consulted 0 of 198 times on GPQA and 1 of 300 on Chartography, where the pairing scored 7 points below the executor alone. Claude Code's own docs give one concrete tiering example — override `Explore` with `model: haiku` — and the general line "For simple subagent tasks, specify `model: haiku`".

**The routing-research caveat** (KQ4). RouteLLM, FrugalGPT, Hybrid LLM, and RouterBench report 35–98% cost cuts, but every result is on single-turn chat, QA, or math with a learned per-query router, the weak model treated as near-free; RouteLLM's router was near random on MMLU until trained on in-distribution labels. None of it transfers to a multi-turn tool-use loop. The one agentic measurement found — Arize with Fireworks, July 2026, 10 models × 40 Terminal-Bench tasks × 6 trials — shows cost per *successful* task diverging from token price (gemini-3.5-flash at $1.233 per success with 91% of failures from the token cap, against GPT-5.5 at $0.636) and a cheap-first escalation ladder beating the best single model on both cost and coverage, results the authors call directional (±6 points). What transfers is the cascade shape — try cheap, verify, escalate — and the loop's gates already supply the verification step.

**SE sub-task evidence by role** (KQ5). Ordered from safest to cheapen to least: bookkeeping (commit messages, summaries, titles) is universal vendor practice with no counter-evidence and no published measurement; read-only bulk exploration is where Anthropic's orchestrator pattern measurably saves ("Work larger than one context window"); test generation is mixed — one 2025 study (SBES) finds small open models competitive on mutation score, older work (Yang et al., 2024-06, known from a search excerpt and not fetched) finds 7B–34B models underperforming EvoSuite on coverage from syntactically invalid tests; the implementer has a measurable tier gap that effort on the stronger model exceeds in the other direction; review and judging is the weakest case. LLM reviewers "frequently misclassify correct code implementation as non-compliant or defective" and more detailed prompts raise the misjudgment rate (Jin and Chen, 2026-02-28); "single-model judges are uneven" and committee composition "matters significantly" (Ullah and Serwadda, 2026). A cheap finder is a false-positive generator for the human gate, which is exactly the "noise costs rounds" mechanism R4 states. Nothing was found on model-tier effects for mutation-test selection specifically (KQ5, Gaps). One practitioner thread reports a cheaper OpenAI model failing `apply_patch` "about 44% of the time per 100 calls, versus under 10%" for the stronger one, prompting a move of the `fixer` role back up (oh-my-opencode-slim #751, 2026-07 to 2026-10).

**Mixed-provider outcomes** (`notes/third-party-providers-and-gateways.md` Q8) are anecdotal: a GLM-5.2 session via OpenRouter ran 45 minutes for $3.36 at a 72% cache rate and "struggled with TypeScript compilation errors" (2026-06-29); a Kimi K2.6 hybrid claims 60–80% savings with Opus "still better for novel reasoning, complex multi-file debugging"; a short HN thread splits between "surprisingly easy" and "CC really needs the Anthropic model special sauce". The failures cluster in long agentic runs, which argues for keeping the strong model on the roles with the longest tool loops.

## 6. Options considered

The options, then the matrix. Each is scored against: ease of configuration within the loop; provider reach; whether it reaches the implementer; fail posture; fit with the three-layer split and the payload rule; maintenance and landscape risk; and observability for the stratum.

1. **Per-role `CAPS` names** (`REVIEW_MODEL`, `VERIFY_MODEL`, …) in `loop.config.md`. Each name is its own token, skeleton row, and inference-map row (`notes/dev-loop-internals.md` §C, Inferences); nine roles with effort doubles that.
2. **One `MODEL_TIERS` table** in `loop.config.md`, role → `tier[@effort]`, read by the engine at each spawn. The favored design.
3. **Shipped `agents/*.md` with frontmatter.** Pre-tiered roles on install; a new payload directory; per-call parameters outrank it anyway; user agents of the same name shadow it (`notes/claude-code-native-surfaces.md` Q2).
4. **Routing Mod** (`agent.spawn` + `turn.step`). Alternative A.
5. **`PreToolUse` routing hook** (`updatedInput` on `Agent`). Alternative B.
6. **Gateway-only with hint headers.** Zero engine change; routes on request class and built-in agent type; cannot tell two custom agents apart ("A user-chosen agent name is never sent") (`notes/third-party-providers-and-gateways.md` Q3).
7. **CCR `<CCR-SUBAGENT-MODEL>` tag.** The engine writes a gateway-specific tag on the first line of each spawn prompt; works only with CCR and only when its models have Descriptions (Q2).
8. **`/model` per step.** Every switch is a full uncached re-read of the parent context (Q7); the implementer is a parent turn, so this is the only non-mod way to reach it, at the price of re-reading 200–950k at each switch.
9. **A second config file** for tiers (JSON sidecar). The guard hook's precedent, but a second seam for a value the engine reads at runtime.
10. **External agent CLIs via Bash** (aider, Codex, OpenCode as steps). Leaves the harness's isolation, permissions, and gates; the role's output re-enters as untrusted text.
11. **Agent-SDK orchestrator.** A rewrite of the loop outside Claude Code; the SDK's `AgentDefinition` carries `model` and `effort` (`notes/prior-art-and-evidence.md` KQ3), but the plugin would stop being a plugin.
12. **Session-wide `CLAUDE_CODE_SUBAGENT_MODEL` only.** One model for every subagent, by env; no per-role shape; does not move the built-in `Explore` (Q8).
13. **The inverted roster.** Option 2 run from the other end: a cheaper or lower-effort session (`/model sonnet`, or `/effort medium`, which §4 says keeps the cache on the 5.5 family) with `MODEL_TIERS` moving the judgment roles *up* (`design: opus`, `finder: opus`, `ac-verify: opus`). No new mechanism, and the only v1 shape that reaches the implementer and the parent's ~62–67% of the bill, since the session model *is* the implementer's; it is where Anthropic's "tune effort first" guidance points (§5), and it is the case that showed `inherit` is safe only as today's behavior (§7.1). Two caveats to score: the parent's own orchestration judgments — status classification, the merge decision, every stop — then run on the cheaper model; and the family-alias quirk (§4) makes `opus` resolve to the session's exact ID when the session is already in that family, so the tier-up is a no-op from an Opus session.
14. **Effort-only v1.** `inherit@<level>` throughout: the same model everywhere, lower effort on the roles that tolerate it. Anthropic's first lever, cache-preserving on the 5.5 family; it moves no model, so none of the provider and fidelity questions arise, and it is bounded by the unknown subagent effort baseline (F198).

## 7. Recommended design

### 7.1 The `MODEL_TIERS` vocabulary

One `CAPS` parameter, `MODEL_TIERS`, bound in `loop.config.md` like `SOURCE_LAYOUT` and `ARCHITECT_TRIGGERS`: the §1 row says `see §N` (or `—` plus a reason), and §N is a list of entries, one per line, in this grammar:

```
<role>: <tier>[@<effort>]

role   ∈ scope | design | explore | finder | recheck | ac-verify | mutation | hermetic
         (fix is reserved for R1's fix agent; implement is reserved for a non-fork implementing
         spawn, which R2's current path does not supply — the engine ignores both until a spawn
         site exists)
tier   ∈ inherit | haiku | sonnet | opus | fable
effort ∈ low | medium | high | xhigh | max
```

The role keys map onto the spawn sites of §3 as follows, and the engine passage is the authoritative map (the skeleton's copy is a courtesy): `scope` is every `SCOPE_AGENT` consult; `design` is every `DESIGN_AGENT` consult, plan-informing and scope-ruling alike; `explore` is any ad-hoc read-only map-the-codebase spawn the parent makes; `finder` is the round-1 fan-out including the floor lens; `recheck` is every fresh decide-by-reading checker that is not the AC-verifier — the step-8 round-2 checker and the Class B limit-case re-checker; `ac-verify` is the AC-verifier Part 1 spawn and its round-2 re-verify, named to match the existing `gate-rounds=ac-verify` sub-slot and to stay clear of the `VERIFY` binding, which is the run-the-app skill and which this key does not touch; `mutation` is the mutation selector/judge; `hermetic` is the step-6 fresh-instance checker. There is no `security` key: under the common binding `SECURITY_REVIEW` is a by-name skill with no spawn, so the key would do nothing, and a key that does nothing is not free — every key is copied into every consumer's skeleton and reached by no later release, so adding one later is free under default-deny (an absent entry inherits) while removing a stranded one is not. `inherit@low` is a legal value — same model, lower effort — and is the entry Anthropic's guidance reaches first.

Resolution is by exact key: one entry per role, and an absent entry resolves to `inherit`. (A route qualifier, `<role>.<route>` resolved most-specific-first, is phase 2 — §7.8 — and default-deny is what makes adding it later backward-compatible.) The default-deny clause, written once in the engine passage and never defended with a list of which roles are safe to tier:

> A role resolves to the tier and effort its entry names. Every other outcome — no entry for the role, an entry whose tier or effort is not one of the names above, a line the engine cannot parse as an entry, two entries for the same key, a `MODEL_TIERS` row that is absent, `TODO`, or `—` — resolves to `inherit`: the engine passes neither `model` nor `effort`, exactly as it does today. An entry that was present and could not be read — a name outside the grammar, an unparseable line, a key that appears twice — resolves to `inherit` with no fall-through to any other entry, not to the other of two duplicates and not to a less specific key, and the journal records the role as `<role>:inherit(unread)`, so that a typo is seen rather than absorbed. If the engine cannot read it, the role inherits.

The safe outcome is named — `inherit`, meaning today's behavior — and everything else lands on it. Safe is exact here: `inherit` is safe because nothing changes from today, not because today's model is the better one. In a cheaper session running the inverted roster (§6, option 13) with `design: opus`, a typo in that entry moves a judgment role *down* to the session model, which is why the fallback must be loud as well as inert — the `(unread)` mark in the clause is what makes it loud. This is the posture the repo's prose rule requires, and it is what bounds the table's stranding risk (§10): a key the consumer's config names and the engine does not know is ignored; a key the engine adds and the consumer's config lacks inherits; in both cases the role behaves as it did before the drift.

Three properties make the alias the right unit of contract. The Agent tool's per-call `model` takes only the four aliases, never a full ID or `inherit` (`notes/claude-code-native-surfaces.md` Q3), so an alias is the only thing a spawn sentence *can* pass. `ANTHROPIC_DEFAULT_*_MODEL` decides what each alias means, and subagent aliases follow those pins (Q6), so the consumer's environment — not the config and not the engine — decides whether `haiku` is Haiku 5.5, Haiku 4.5 on Bedrock, `deepseek-flash`, or a LiteLLM `model_name`. And a pinned alias carries its `[1m]` suffix "including … subagents whose `model` frontmatter names the alias" (Q6), so the window travels with the tier — stated for frontmatter; the per-call parameter is not named in that sentence, which is a small gap to confirm with claim 1 (§10).

### 7.2 The engine change

One canonical passage in `loop-engine.md` core carries the grammar, the resolution order, the default-deny clause above, and the journal rule. Each spawn site then carries one sentence that names its role and points at the passage, never restating the rule — the multi-site invariants that drifted in #35 (`plugins/CLAUDE.md`, via `notes/dev-loop-internals.md` §D) are the hazard this avoids. The sites: `SCOPE_AGENT` at steps 1/3/5 and `DESIGN_AGENT` at 4/5/8 in core; the hermetic checker in core step 6; finders and the fresh re-checker in `phases/reviewing.md`; the AC-verifier and the mutation selector in `phases/accepting.md`; the Class B re-checker in core. `explore` is the exception, because it has no spawn site of its own — core names `Explore` only inside a Budget-note example (`loop-engine.md:1633`) — so its sentence is one general sentence in core's "Tool surface" section covering any ad-hoc read-only spawn the parent makes, rather than a site-by-site rule for spawns the engine never licenses by name. The sentence's shape: *spawn this agent with the `model` and `effort` that `MODEL_TIERS` resolves for role `<role>`; pass neither when the role resolves to `inherit`.* The Agent tool's own `effort` description says to set it "ONLY when the user, or instructions such as CLAUDE.md or a skill, explicitly ask" (Q3); the engine is a skill, and this sentence is that explicit ask.

Two things the passage must not do. It must not name `ANTHROPIC_DEFAULT_HAIKU_MODEL`, `CLAUDE_CODE_SUBAGENT_MODEL_FORCE`, or any other harness variable literally: `CapsVocabularyTests`' `_UNDERSCORED` regex flags every underscore-joined ALLCAPS token in core, the units, and `SKILL.md` as a binding the skeleton must offer, and growing `ALLOWED_NON_BINDINGS` is "almost always the wrong fix" (§C). The passage says "a tier name is resolved by the harness and the consumer's environment"; the README carries the variable names. And it must not tier the built-in `Explore` by default (R4's caution): the `explore` key exists so that a consumer can. R4's ground for the caution — that on a subscription `Explore` runs the main model — holds for the environment variable but not for the per-call parameter, which claim 1 (§10) verified moves a built-in `Explore` spawn to Haiku under a Max subscription.

The journal rule: the `- Budget:` line gains a `models=<role>:<tier>[@<effort>],…` slot carrying, for each role the engine spawned, the values it *passed*, `inherit` written literally and `inherit(unread)` where an entry existed and could not be read (§7.1). The slot is not named `roster`: that is already the engine's term for step 8's lens roster — 31 occurrences across core and `phases/reviewing.md`, test-pinned — and a second meaning for it would be the kind of drift the multi-site invariants exist to prevent. The Budget line's existing slot rule governs it: an absent slot does not mean zero (`loop-engine.md`, the constraint under "Notes on any slot"), so an omitted `models=` reads as unknown, and a role missing from it is unknown, not `inherit`; the slot makes no completeness claim about which roles were spawned. This is an intent record in the sense the cost review gives every ledger count (§5.4: "Treat every ledger count as an intent record"); the transcript is the instrument, and `stratum.py` already records subagent strata from it. The slot is what makes a prose-compliance failure visible (§10), and it is the intent column the benchmark reads beside the transcript — not the stratum itself (§7.9).

### 7.3 The `/init-loop` skeleton

The §1 binding-table row, in the skeleton's exact format (`notes/dev-loop-internals.md` §C), with no environment-variable name and no step number, both of which the skeleton's maintainer rules forbid:

```
| `MODEL_TIERS` | see §N | per-role model tier and effort for the subagents the engine spawns, as `role: tier[@effort]` lines. A role the section does not name, or names with a value the engine cannot read, gets no model or effort passed — the behavior before this row existed — and the journal marks an entry it could not read, so an empty or half-edited section changes nothing and a typo is visible rather than absorbed. The tier names are the harness's own model aliases; what each one resolves to is your environment's choice, never this file's. Ships with every role `inherit`; change a row only after measuring it |
```

The inference-map row:

```
| `MODEL_TIERS` | cannot be inferred from the repo; emit §N with every role `inherit` — the behavior-neutral default. A consumer that has pinned the harness's model aliases to another provider changes nothing here; the tier names stay the same |
```

And §N itself in the skeleton, every role `inherit`, so a new consumer sees the vocabulary without any role changing model:

```
scope: inherit
design: inherit
explore: inherit
finder: inherit
recheck: inherit
ac-verify: inherit
mutation: inherit
hermetic: inherit
```

The skeleton default is deliberately a concrete value and not `TODO(init-loop)`: the skeleton's own banner reads a `TODO` as "a blank that escalates", so a `TODO` here would stop every fresh consumer at its first spawn (§C, Inferences). The evidence bar for the skeleton is higher than for the engine because no release, CI check, `/init-loop` re-run, or re-install reaches a consumer's config (root `CLAUDE.md`, #30), and `inherit` is the one value that needs no evidence.

### 7.4 What `CapsVocabularyTests` needs

The test scans core, the units, and `SKILL.md` for `_UNDERSCORED` tokens and requires each to appear somewhere in `init-loop.md` (`notes/dev-loop-internals.md` §C). `MODEL_TIERS` matches the regex by inspection — `[A-Z][A-Z0-9]*` takes `MODEL`, `(?:_[A-Z0-9]+)+` takes `_TIERS` — so once the engine names it the test goes red until the skeleton row lands, and green after. Green does not mean the inference-map row exists or that §N's Notes make sense; the test is one-directional by design. Running the suite after the skeleton row is the discharge of claim 2 in §10. Phase 1 adds one small test in `CapsVocabularyTests`' direction: every role key on the engine's grammar line appears in the skeleton's §N. That is an identity coupling between two literals, within the prose-guard ceiling (`tests/CLAUDE.md`) — it pins that the skeleton offers every key the engine reads, and nothing about whether any key is wired to its spawn site or passed correctly, which no test over prose can hold. Nothing else in the suite is touched by phase 1: no new payload file (`_PAYLOAD_INVENTORY` unchanged), no new hook (`PluginIdentifierTests` unchanged), no new unit (`PhaseIndexIdentityTests` unchanged). v1 is therefore clean under the stdlib-only rule by construction — no payload file, no hook, no non-stdlib code — and the question §8 raises about a `.js`/`.ts` mod is phase 4's, not reached here. `test_init_loop_md_contains_no_engine_step_number` is why the rows above name no step. `test_payload_readme_is_identical_to_the_front_door` is why the README edits below land in both copies in one commit.

### 7.5 README changes

The status block is untouched in phase 1 — no version bump ships with the vocabulary alone; it ships with the release that carries it. The trust-model section ("What the loop can do to your repo") gains one statement, in the same posture as its existing plan-gate paragraph: *a tier the engine cannot read makes the role run as it did before the table existed — no model or effort is passed — and the journal says so; the loop never routes a request to a provider — the harness's model aliases are the whole of what it passes, and what those aliases resolve to is your environment's setting.* A new section, "Per-role model tiers", carries the consumer-facing half for phase 1, scoped to the aliases on the consumer's current provider: the `MODEL_TIERS` grammar; the inverted roster as a supported v1 shape (§6, option 13); the plain statement that in v1 the code, tests, and docs an issue needs are written on the session model, and the only lever on them is that model and its effort (§7.8); and the two harness variables that override the table from outside it — `CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1`, which makes the per-call `model` ignored, and `CLAUDE_CODE_EFFORT_LEVEL`, which outranks the per-call `effort` and which three provider guides set to `max` (§10). The "Bring your own models" heading, the provider profile (§7.6), the economy table (§7.7), and the fidelity caveats from `notes/third-party-providers-and-gateways.md` Q5 are held for phases 2 and 3 (§7.8): phase 1 ships no profile and no table, because an unrun profile and an unmeasured table are each a recommendation with a label on it. The sentence Anthropic's gateway page requires for honesty lands with the profile: Anthropic "doesn't support routing Claude Code to non-Claude models through any gateway"; this loop has not measured it either.

### 7.6 The provider profile

The provider dimension lives outside the engine, in a settings `env` block, which is the only settings surface that reaches the API client (`notes/claude-code-native-surfaces.md` Q10; a plugin `settings.json` cannot ship `env`). The documented default place is the per-user one — `.claude/settings.local.json` in the repo, or the user's own `~/.claude/settings.json` — because a committed `.claude/settings.json` moves every collaborator's every session in that repo to the provider, loop or not, and overwrites their shell exports (Q10). The committed project file is presented only as a deliberate team choice, taken knowing that. Either way the block applies after workspace trust in interactive sessions and at startup under `-p`. This is phase-3 material (§7.8), shown here so the shape is reviewable; the shape is the one the provider guides converge on (`notes/third-party-providers-and-gateways.md` Q1), with DeepSeek as the worked example. DeepSeek's own guide sets every pin to `deepseek-flash[1m]`; the example below points the `opus` and `fable` tiers at `deepseek-v4-pro` instead, to show a two-model profile. `ANTHROPIC_AUTH_TOKEN` is set in your shell or the local file and never committed, so it appears in neither example; `ANTHROPIC_API_KEY=""`, which the OpenRouter and Vercel guides set "to prevent conflicts", is likewise a per-user step, because committing it breaks every collaborator who authenticates with an API key. Two variables from DeepSeek's guide are omitted on purpose: `CLAUDE_CODE_EFFORT_LEVEL=max`, because it outranks the per-call `effort` (§4) and would silently defeat every `@effort` entry in the table while the journal recorded an effort that never ran; and `CLAUDE_CODE_SUBAGENT_MODEL`, because it decides every spawn the table leaves at `inherit`, which would make `inherit` mean the guide's choice rather than today's behavior:

```json
{
  "env": {
    "ANTHROPIC_BASE_URL": "https://api.deepseek.com/anthropic",
    "ANTHROPIC_DEFAULT_OPUS_MODEL": "deepseek-v4-pro",
    "ANTHROPIC_DEFAULT_SONNET_MODEL": "deepseek-flash[1m]",
    "ANTHROPIC_DEFAULT_HAIKU_MODEL": "deepseek-flash",
    "ANTHROPIC_DEFAULT_FABLE_MODEL": "deepseek-v4-pro"
  }
}
```

The README's instruction, and it is an instruction rather than a description of what the guides do: pin all four aliases — `FABLE`, `OPUS`, `SONNET`, `HAIKU` — before calling a profile complete. The guides do not all do this. Z.ai's pins `OPUS` and `SONNET` only, Ollama's uses `--model`, and an unpinned `fable` sends a `claude-*` ID upstream, which DeepSeek maps to `deepseek-flash` server-side (its `claude-opus*` → `deepseek-v4-pro`, everything else `claude*` → `deepseek-flash`) and a stricter upstream may reject outright (Q1, Q3). And on a profile that pins every alias to one model — DeepSeek's and MiniMax's as published, Kimi's but for `HAIKU` — the table changes nothing, because every tier is the same model; a consumer on such a profile gets provider portability from the pins and no tiering from the table until the profile names a second model. Mixed providers in one session need a name-routing gateway, because one session has one `ANTHROPIC_BASE_URL` — "changes where requests are sent, not which model answers them" (Q3). With LiteLLM the four pins name `model_name` entries that map to `openai/…`, `gemini/…`, or `anthropic/…` upstreams; with Bifrost or Vercel they name `provider/model` IDs; with Portkey the provider is an `x-portkey-provider` header slug and the pins carry the model ID. OpenAI and Gemini have no Anthropic-format endpoint of their own and are reached only this way; xAI's is deprecated (Q1).

The fidelity caveats the README must carry, from Q5: the recurring real-world defect is reasoning-state round-tripping on tool calls (DeepSeek's `reasoning_content`, Gemini's `thought_signature`), open in CCR since 2026-05 and 2025-12, which breaks on the second tool turn and so surfaces only in agentic use; Claude Code treats an unrecognized model ID as a current Claude model and sends adaptive thinking and mid-conversation `role: "system"` entries, so strict upstreams 400; prompt caching is lost silently on several paths; an unrecognized ID is assumed to have a 200K window unless it carries `[1m]`. Non-Claude models are riskiest exactly on the tool-heavy roles, which is a second reason — beside R4's — to keep `finder`, `recheck`, and `design` on `inherit` under any provider profile.

### 7.8 What v1 does not address, and the path

The implementer. Step 6 runs in the parent, so the code, the tests, and the docs an issue needs are written on the session's model at the session's effort; that is set by `/model` and `/effort`, or a `modelSettings[<model>].effortLevel`, outside all three layers. So in v1, docs and code are written on the session model, and the only lever on them is that model and its effort — which is the inverted roster (§6, option 13), and the README says so in those words (§7.5). The path to a table-addressable implementer runs through R1 only: R1's fix agent is a writing spawn in an isolated copy and becomes the `fix` role, the one key reserved on evidence. `implement` is reserved too, but labeled: it requires a non-fork spawn and is not on R2's current path. A forked phase runs on the main model and ignores both parameters (`notes/claude-code-native-surfaces.md` Q3 and the fork table); the only way to set a fork's model is a skill's `model:` frontmatter, which is static in the payload, so `MODEL_TIERS` cannot feed it; and a non-fork implementing spawn loses the shared cache that makes a fork cheap and takes on D017's four isolation duties and the staging window (`notes/dev-loop-internals.md` §A, Inferences). Both keys stay in the grammar so that the table does not change shape when a spawn site lands. The route qualifier `<role>.<route>` is phase 2 as well: default-deny makes adding it backward-compatible, its one proposed use, `finder.docs`, is unmeasured, and docs review is already "one light pass".

Phasing:

1. Vocabulary, spawn sentences, the journal `models=` slot, the skeleton row and inference-map row, the key-identity test (§7.4), this repo's own `loop.config.md` §N (a human PR), the trust-model statement, and the README "Per-role model tiers" section — every role `inherit`; no profile, no economy table. Behavior-neutral; ships in the next release.
2. The economy table and the route qualifier: a row is promoted to a measured preset once #274 has replayed fixtures under it with #272's quality outcome beside the cost and the §7.9 decision rule is met; the qualifier lands with the first row that needs it.
3. "Bring your own models": provider-profile documentation with the fidelity caveats, and one worked profile the maintainer has actually run (a Haiku/Sonnet/Opus profile on the Anthropic API is the first; a LiteLLM profile the second). The heading and the profile wait for this phase so that the README never carries an unrun profile.
4. Optional: a routing mod (Alternative A) for parent-thread routing and per-role cost attribution, once mods leave early access and the decision-log entry §8 asks for exists.

#281 should split along the line between phases 1 and 2: a vocabulary issue, behavior-neutral and meeting #281's AC3 by construction, and a tiering issue that closes only on a measurement under the §7.9 rule. Keeping them in one issue would gate a behavior-neutral change on a benchmark that has not run.

### 7.9 Measurement plan

Primary outcome: USD per completed issue, which the cost review already proposes as the program's primary metric (§1), priced by `tree_cost.py --sessions`, which prices each turn on its own model's weights and therefore handles a mixed set of models. Quality outcome: #272's instrument (fix-up commits within 14 days per merged PR, escalations per issue, F-comment attribution). Stratum: the resolved model IDs and effort of the parent and of each subagent, taken from the session transcript — never from the `models=` slot. The slot records alias names and intent: `haiku` is Haiku 5.5 for one consumer and `deepseek-flash` for another, and `CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1` or `CLAUDE_CODE_EFFORT_LEVEL` can make the record differ from what ran (§10). So `(parent model, effort, resolved subagent models and efforts)` is the stratum — §5.6's rule read on the transcript, and the substance of #281's AC2 — and the slot is the intent column read beside it to spot compliance gaps. Today `stratum.py` records subagent model strata but never groups by them, so two sessions with identical parent strata and different subagent models would pool, and every measurement of tiering is inadmissible until that changes. Harness: #274's paired benchmark, both arms on one stratum, with the intended table named in the pre-registration. Four preconditions, one new and three from `notes/dev-loop-internals.md` §B. The new one: is subagent effort observable in the session JSONL? Claim 3 (§10) could not see it from inside the subagent, and until it is readable from the transcript, effort can be stratified only on the parent's side and the `@effort` half of the table cannot be verified to have run. Then §B's three: `LOAD_TOKENS` has no 0.4.0 rows, so `engine_cost.py` refuses every 0.4.0 session until one is measured (`tree_cost.py` has no such dependency); a `PRICING` entry must exist for every model a tier resolves to or whole-tree pricing refuses (D016); and the dependency chain is #272 → #273 → #274 → #281.

The modeled expectation, stated as modeled. R4's 7–15% whole-tree is the anchor, under its own rule that judgment roles stay on the main model; on the 0.3.1 medians that is $1.2–2.6 per loop session and $2.5–5.3 per vote session. Anthropic's −32% per attempt is the ceiling on what cheapening subagents can do in a harness where subagents carry the bulk work; here the subagent share bounds any tiering effect at 33–38% whole-tree even if every subagent cost went to zero. Against that, one review round is roughly $4–6 of an $18–36 iteration by the notebook's cost model (`notes/dev-loop-internals.md` §A, Inferences), so a tiering change that adds one round per issue on average wipes out the whole modeled saving. That asymmetry is why the first measured table should change the roles whose errors cost tokens, not rounds, and why rounds per issue is a pre-registered outcome rather than a thing to notice afterward.

The decision rule, pre-registered before the first arm runs, with the placeholders the benchmark fills: an economy row is promoted from §7.7 to the README when it saves **≥ X%** whole-tree USD per completed issue on the paired benchmark *and* rounds per issue is non-inferior within a margin of **Y** rounds. Rounds per issue is a non-inferiority outcome, not a secondary: one extra review round is ≈ $4–6 by the figure above, which wipes out the modeled saving, and it is already on the `- Budget:` line as `gate-rounds=`, so it costs nothing to collect. Power: a modeled $1.2–2.6 per session against medians from n=5 is underpowered for any plausible per-session spread, and a result from an n chosen after the data is in is not a promotion. The benchmark must state the n it needs for X at the margin Y before it runs, or estimate it from the σ #209 is to measure; until one of those exists, "unmeasured" is the only honest status for every row.

For `.claude/specs/decisions.md`, append-only, after D017:

```
## D018 — 2026-10-31 — Model tiers are a config table of alias names; unknown resolves to inherit; the engine never names a provider

**Context.** Subagents are 33–38% of the whole-tree bill and every one runs the parent's model (F198; R4). The Agent tool's per-call `model` takes only the four aliases; `ANTHROPIC_DEFAULT_*_MODEL` pins what each alias means, and the third-party provider guides converge on that recipe (`OPUS`/`SONNET`/`HAIKU`, increasingly `FABLE`), not uniformly and in some cases pinning every alias to one model. Step 6 runs in the parent thread (D017), and a forked phase ignores both spawn parameters, so no fork can carry an `implement` role. #281 proposed pinning user-global agent frontmatter, which the engine forbids the orchestrator from editing, and tiering parent turns, which are not spawns.

**Decision.** (1) One `CAPS` parameter, `MODEL_TIERS`, in `loop.config.md`: `role: tier[@effort]` with role ∈ `scope|design|explore|finder|recheck|ac-verify|mutation|hermetic` and tier ∈ `inherit|haiku|sonnet|opus|fable`; one entry per role, resolved by exact key. Any outcome the engine cannot read as an entry resolves to `inherit`: the engine passes neither `model` nor `effort`, exactly as it does today. An entry present but unreadable, or two entries for one key, resolve to `inherit` with no fall-through to any other entry, and the journal records the role as `inherit(unread)`. The rule is not defended with a list of safe roles. (2) The engine passes the resolved values on each spawn and journals a `models=` slot on the `- Budget:` line, under the existing rule that an absent slot reads as unknown; it names no provider and no harness variable. (3) The skeleton ships every role `inherit`; a key is added only with a spawn site, because a stranded key cannot be removed from consumer configs. (4) Provider choice is a settings `env` block — per-user by default, committed only as a team choice; the token is never committed; mixed providers need a name-routing gateway. (5) No default tier changes before #274 measures it on the transcript's resolved models and efforts with #272's quality outcome, under a pre-registered saving threshold and a rounds-per-issue non-inferiority margin. (6) `fix` is reserved for R1's fix agent. `implement` is reserved but requires a non-fork spawn that R2's current path does not supply; in v1 the implementer runs on the session model, and the inverted roster — a cheaper or lower-effort session with judgment roles tiered up — is the supported v1 shape that reaches it. (7) The route qualifier `role.route` is deferred to phase 2.

**Why.** The alias is the only unit a spawn can pass and the only one the providers remap, so it is the one portable contract. Default-deny with today's behavior as the safe outcome (unknown ⇒ no parameter passed) is the repo's prose rule applied to the one place a silent change would be invisible; `inherit` is safe as *today's behavior*, not as a quality floor — in a cheaper session a typo moves a judgment role down — which is why the fallback is loud as well as inert. A second config file, per-role `CAPS` names, `/model` per step, external CLIs, and an SDK orchestrator were rejected on the matrix in `docs/research/model-selection-2026-10-31.md` §6; a routing mod and a `PreToolUse` hook are recorded there as the alternatives that add parent-thread reach and enforcement respectively.
```

## 8. Alternative A — a routing Mod

A mod is an ordinary plugin whose `hooks/hooks.json` names a `modules` entry pointing at one ES module exporting `register(on, options)`; its handlers run in-process as a middleware chain over engine events, shipped publicly in v2.1.287 and marked early access (`notes/hooks-and-mods.md` KQ1). Two events do the routing. `agent.spawn` fires when "A subagent or an agent team teammate is about to start" and a hook may return `next({ ...e, model })` to choose its model — alias or full ID — or `{ deny: reason }`; the sub-agents page confirms that a mod's `agent.spawn` choice replaces the per-invocation parameter (KQ2). `turn.step` fires when "One request is about to go to the model" and may rewrite `model` or `effort` on every request, main loop and subagent loops alike; its result carries `usage` with the model that answered (KQ2, KQ5).

What it uniquely enables. First, main-loop routing per step: `turn.step` is, by the note's reading, the only place where "change the main-session model mid-turn" is a yes — settings hooks cannot, and `/effort` changes start on the next message (KQ2, Inferences) — which means the parent-thread implementer could run on a different model than the planner without the engine changing — at the price of a full uncached re-read on every switch, since each model has its own cache (`notes/claude-code-native-surfaces.md` Q7). Second, per-role cost attribution: `turn.step` usage keyed by `e.agentId`, with `usage.model` naming the answering model, is the only in-process source of per-subagent cost; settings hooks carry no token or cost data, and the status line's `cost.total_cost_usd` is one session-wide number (KQ5). Third, enforcement independent of the orchestrator: a mod that reads the config and sets `model` at `agent.spawn` makes the roster true whatever the spawn sentence said.

Config shape: the same `MODEL_TIERS` section, read by the mod through `$.fs` and matched to a role by convention — `e.subagentType`, `e.name`, `e.description`, or a role marker on the first line of `e.prompt` (the shape CCR's tag uses) — plus an optional per-step table for the main loop (`plan: opus`, `implement: sonnet`) that the mod would key off a step marker the engine writes. The last part is the weak link: nothing today tells a mod which pipeline step the parent is on, and the step→turn mapping has never been measured (`cost-review-2026-10-26.md` §6).

Packaging in the payload: `plugins/dev-loop/hooks/hooks.json` gains `"modules": ["./register.ts"]`; one TypeScript file; `_PAYLOAD_INVENTORY` gains it; no Node, npm, bundler, or build step, because Claude Code loads `.js` and `.ts` directly (KQ1). The repo's stdlib-only rule does not settle this, and should not be read as if it did: the rule was written for Python — "stdlib" is Python's standard library, and its stated reason is that the hook and the suite run under bare `python3` — so a `.js`/`.ts` mod is outside its terms rather than inside or outside its letter. What is plain is the consequence: the bare-`python3` suite cannot run a JavaScript module, so the mod would be the payload's first untested executable. That needs a decision-log entry before the file lands, not a reading of the existing rule. (`claude plugin validate` would list its `env reads:`/`env writes:` before install — KQ6 — which is a disclosure, not a test.) v1 raises none of this: phase 1 adds no payload file, no hook, and no non-stdlib code (§7.4).

Fail posture: a hook with no `.catch` that throws, times out (10 s), or returns the wrong shape is skipped and the subagent starts on the engine's own resolution — fail-open, which is the right posture for routing and the wrong one for enforcement; `.catch` returning `{ deny }` opts into closed, and `claude plugin validate` flags a gating hook without one (KQ7). `CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1` outranks a hook's choice — "that outranks a workflow agent's, a hook's included" (KQ2) — so the consumer keeps a kill switch. `AgentSpawnInput` has no `effort` field, so a mod cannot set a subagent's effort at spawn; the two indirect routes (`tool.call` on `Agent` rewriting `effort`; `turn.step` keyed on `e.agentId`) are inferred, the second documented as rewritable (KQ2, Inferences).

The trust-surface disclosure the README would need: "A mod is code that runs with your permissions. It can read and write your files, start processes, and make network requests." "Mods aren't sandboxed." On a machine without managed settings, a mod can approve a call that an `ask` rule would prompt for or that a `PreToolUse` hook blocked (KQ7). The existing trust-model section describes a Python hook that covers `Write` only and fails open until opted in; a mod is a materially broader surface and the section would have to say so.

Early-access risk: the type declarations are headed "EARLY ACCESS: this surface may change between releases without notice"; the public reference covers the CLI "as of v2.1.290"; `agent.spawn` gained teammates in 2.1.289, workflow agents in 2.1.292, resume in 2.1.299, and prompt/model rewriting for workflow agents in 2.1.300 — four changes in thirteen releases (KQ2). An alias at `turn.step` "went out as written" before 2.1.309. Goose's removal of its lead/worker switching is the landscape precedent for in-session automatic switching not surviving (`notes/prior-art-and-evidence.md` KQ2).

When to revisit: when mods leave early access; when `AgentSpawnInput` gains `effort`; when phase 2's benchmark shows a measured saving that per-role attribution would sharpen; or when the journal `models=` slot shows the orchestrator omitting the spawn parameters often enough that enforcement is worth JS in the payload. Until then the mod is phase 4, optional, and its absence changes nothing.

## 9. Alternative B — a `PreToolUse` routing hook

This is the compliance backstop for §7, not a peer of it: it can enforce the *values* the table binds, but it identifies the *role* by the same prose convention §7's spawn sentence relies on, so it backs the sentence up rather than replacing it. The mechanism mirrors the plugin's existing guard: a stdlib Python script registered in `hooks/hooks.json` as a `PreToolUse` matcher on `Agent` (the subagent tool's documented name), reading a sidecar JSON at `${CLAUDE_PROJECT_DIR}/.claude/loop.model-tiers.json`, and returning `hookSpecificOutput.updatedInput` with `model` and `effort` set from the table (`notes/hooks-and-mods.md` KQ3). `updatedInput` "Replaces the entire input object, so include unchanged fields alongside modified ones"; since 2.1.300 it is validated like Claude's own input, so `model` must be one of the four aliases and `effort` one of the five levels or the call is denied. Because the rewritten value becomes the per-invocation parameter, it wins over frontmatter and `CLAUDE_CODE_SUBAGENT_MODEL` unless `_FORCE=1` — a consequence of two documented rules, not a documented statement (KQ3, Inferences). No page shows the Agent tool's input being rewritten; the only Agent-specific statement about overriding the per-call model names a mod's `agent.spawn`. The note's label: "Treat it as plausible and testable, not as supported."

Role identification is the weak link. The hook sees `prompt`, `description`, `subagent_type`, `model`, `effort`, `name`, `isolation` (KQ3). None of those is a role: `subagent_type` is `general-purpose` for most of the loop's spawns, and `description` and `prompt` are free text the orchestrator writes. The hook would have to match a convention the engine commits to — a role token in `description`, or a first-line marker in `prompt` — which means the hook's correctness rests on the same prose compliance it was meant to enforce. It enforces the *value* independently of the orchestrator, but not the *role*.

The sidecar's own validation must be default-deny in the loader, as `guard_append_only.py`'s is: a role entry whose tier is not one of the four aliases, or whose effort is not one of the five levels, must pass the call through unchanged, never be forwarded — because a forwarded invalid value is denied by the harness's validation, and a denied spawn is a stalled gate. That is the one place this hook's fail-closed edge differs from the guard's: an invalid rewrite does not fail open, it blocks.

Fail posture: settings hooks fail open by default — non-zero exits other than 2, timeouts, and malformed JSON let the action proceed — and `onFailure: "block"` (v2.1.295+) flips to closed (KQ7). Fail-open is correct here: a missing sidecar or a crash leaves the orchestrator's own `model`/`effort` in place, which is exactly what §7 alone would have done — the hook's absence changes nothing, and the `models=` slot still records what the orchestrator passed. `onFailure: "block"` would stall every spawn on a hook bug. Whether `onFailure` applies identically to plugin-shipped `hooks/hooks.json` entries is not stated in the text the note read (KQ7, Gaps). The multi-hook caveat: "When multiple `PreToolUse` hooks return `updatedInput` to rewrite a tool's input, Claude Code doesn't merge the rewrites or guarantee which rewrite the tool runs with" (KQ3). A consumer with its own Agent-rewriting hook gets an undefined winner, silently.

Payload and suite: a new `hooks/*.py` file enters `_PAYLOAD_INVENTORY`; it must be `${CLAUDE_PLUGIN_ROOT}`-relative in `hooks.json` or `PluginIdentifierTests` goes red; it is bound by the stdlib-only rule and would take a test file in the style of `test_guard_append_only.py`; and it introduces the second config file the coordinator rejected for *tiers* — which is why it is an alternative, not the design.

When it would be worth adding, as an enforcement layer on top of §7 rather than instead of it: when the journal `models=` slot and the transcript disagree often enough to matter — that is, when `stratum.py` shows subagents on the session model in sessions whose config bound a tier — and when the role convention has proven stable enough that matching on it is no worse than the spawn sentence it backs up. The order is the opposite of what intuition suggests: ship the vocabulary first, measure compliance through the slot, add the hook only if the measurement says to.

## 10. Risks and open questions

**Prose compliance.** The spawn sentence is an instruction the orchestrator may omit, and nothing in the harness enforces it. The journal `models=` slot exposes an omission in two ways: a role spawned with no entry in the slot — which reads as unknown, not as `inherit` — or an entry that names a tier while the transcript's subagent record names the session model. The first is visible in the ledger; the second needs `stratum.py` grouping by resolved subagent model (§7.9; #281 AC2). Neither is a guard the suite can hold — by the prose-guard ceiling, a test can pin that a spawn site *names* the parameter, never that the right tier was passed (`notes/dev-loop-internals.md` §D, Inferences).

**The family-alias quirk.** `opus` in a per-call parameter resolves to the main model's exact ID when the main model is an Opus, and on a non-Anthropic provider whenever the family cannot be told (`notes/claude-code-native-surfaces.md` Q3). Under an Opus 5.5 parent — the account default on every plan — `role: opus` means `inherit` in practice, `[1m]` included. The README should say so, the economy table should not use `opus` to mean "cheaper than Fable", and the inverted roster (§6, option 13) moves a role up with `opus` only when the session is not already in the Opus family — from a Sonnet or Haiku session it does what it says; from an Opus session it is a no-op.

**`FORCE` and `EFFORT_LEVEL` overriding the config.** `CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1` makes the per-call `model` ignored, and `CLAUDE_CODE_EFFORT_LEVEL` outranks the per-call `effort` (§4), so a consumer who sets either silently defeats the corresponding half of every `MODEL_TIERS` entry, and the engine cannot tell: the `models=` slot records what was passed, not what ran. The second is the likelier accident: the DeepSeek, Kimi, and MiniMax guides each set `CLAUDE_CODE_EFFORT_LEVEL=max` (`notes/third-party-providers-and-gateways.md` Q1), so a consumer copying a guide defeats every `@effort` entry and the journal records an effort that never ran. Both are consumer-side settings by design — the first a kill switch, the second a guide's convenience; the transcript is the truth, the stratum is taken from it (§7.9), and the README names both variables as ones that override the table (§7.5).

**Subscription usage-limit accounting is unverified.** Subagent requests "count toward the same usage limits as your main conversation"; no official page states a per-model consumption rate; the existence of "You've hit your Opus limit" and a separate weekly Fable limit implies some families are metered separately, but that is an inference from the message taxonomy (Q8). "Haiku subagents cost less of my Max limit" cannot be claimed.

**Non-Claude fidelity on tool-heavy roles.** The reasoning round-trip defects (Q5) break on the second tool turn and have stayed open for months in CCR; no independent, dated measurement of tool-call success per non-Claude model under the Claude Code harness exists. A provider profile that puts a non-Claude model on `finder` or `design` is unmeasured and risky in exactly the way the evidence predicts.

**Anthropic's "unsupported" stance and the marketing wording.** The gateway page: Anthropic "doesn't support routing Claude Code to non-Claude models through any gateway". The legal page restricts credentials (no subscription OAuth through third parties), not backends; the note found no statement that permits third-party backends either, and HIPAA coverage excludes gateway-routed sessions (`notes/third-party-providers-and-gateways.md` Q6). The honest README sentence is the one in §7.5: the loop passes the harness's model aliases and nothing else; what they resolve to is your environment's choice; Anthropic does not support non-Claude backends through any gateway; this project has not measured them.

**Skeleton wording stranded in consumer configs.** The §N key list is copied into every onboarded repo and reached by no later release. The default-deny clause makes drift resolve to today's behavior in both directions (§7.1), but a consumer whose config still carries a renamed key will believe it tiers a role that inherits — and that case is silent, because the engine sees an absent entry for the new name, not an unreadable one, so no `(unread)` mark is written. This is why adding a key is free and removing or renaming one is not (§7.1), and why `security` was dropped before the list first shipped rather than after. Mitigation: the engine passage is the authoritative key list, and the journal `models=` slot shows what actually resolved.

**Effort on a tier whose provider resolution has no effort support.** Haiku 4.5 (the `haiku` alias on Bedrock/Vertex/Foundry) does not support effort at all; the session rule is "falls back to the highest supported level at or below", but what the per-call `effort` parameter does on a no-effort model is undocumented (Q4, Q9). Treat `@effort` as an intent and expect the documented step-down.

**The three load-bearing claims** `notes/PROGRESS.md` says to verify before finalizing, and their status here:

1. The per-call `model: haiku` is honored on a built-in `Explore` spawn. **Verified 2026-10-31** (CLI 2.1.314, Max subscription, parent Fable 5.1): an `Explore` spawned with `model: haiku` reported its own system-prompt model sentence as "You are powered by the model named Haiku 5.5. The exact model ID is claude-haiku-5-5." The docs say `CLAUDE_CODE_SUBAGENT_MODEL` alone does not move Explore and that a same-named custom agent does (Q8); the per-call parameter is stated nowhere for a built-in, so this is an observation on one version, not a documented contract — re-check at each minor release (§11).
2. `CapsVocabularyTests`' regex accepts `MODEL_TIERS` once it is in `init-loop.md`. **Verified 2026-10-31**: the `_UNDERSCORED` pattern (`tests/test_repo_consistency.py`, `CapsVocabularyTests`) extracts `MODEL_TIERS`, and the test requires only that the literal appear anywhere in `init-loop.md`. Discharged for good by running the suite after the row lands.
3. The `effort` per-call parameter works on a general-purpose spawn. **Accepted, not observed** (2026-10-31): a general-purpose spawn with `model: sonnet` and `effort: low` ran on `claude-sonnet-5-5` (the model half is verified), but effort is an API request parameter that no sentence of the subagent's prompt reports, so the probe could not see it. The docs date the parameter to v2.1.292 and say it "overrides the `effort` field and stays in effect when the subagent is resumed" (Q3); `/tasks` names the model and effort on a subagent's row (v2.1.242+), so one reading after a spawn with `effort` set is the remaining check.
